Backend tests are plain `node:test` files colocated with the source (`*.test.js`), run with `cd backend && npm test` (`node --require ./testSetup.js --test`). **`backend/testSetup.js` is load-bearing — don't drop the `--require`.** It repoints `console` at stderr for the duration of a test run, because the test runner uses each child's *stdout* to carry v8-serialized result frames: an application log line written mid-frame splits it, and the runner dies with `Unable to deserialize cloned data due to invalid or unsupported version`. That surfaces as a whole test *file* failing at its boundary while every test inside it passed — an infrastructure-looking blip with no bad assertion behind it, which is exactly what makes it easy to wave off as "just a flake" and re-run. Output is redirected rather than silenced, so logs are still visible when debugging. Linting/formatting is [Biome](https://biomejs.dev) via a single root `biome.json`; the `frontend/` and `backend/` packages each also expose `npm run lint` / `npm run format` that shell out to the same root-installed Biome.

**A test that needs a *real* server spawns it through `backend/test/helpers/spawnServer.js` — never with a hand-picked port.** Five files (`cors-env`, `api-cache`, `schema-boot`, `rateLimit-proxy`, `ipv6-boot`) run `src/server.js` as a child process and drive it over HTTP, and `node --test` runs test *files* in parallel, so two files naming the same port race for the bind. That already happened once, during PR #33's review rather than on `main` (0XC-275): the loser died with `EADDRINUSE` and failed with `ECONNREFUSED` — and the subtler half is worse, since each file's `/health` poll could instead succeed against the **other** file's server and go on to assert against a process booted with different env (`DATABASE_URL`, `FRONTEND_URL`, `YTDLP_FORCE_IPV4`), yielding a false pass or a failure pointing at the wrong cause. The helper takes the choice away: it always spawns with `PORT=0` (OS-assigned) and reads the **actually bound** port back off the child's `🚀 Server running on http://localhost:<port>` line, so `src/server.js` must keep logging `server.address().port` there rather than echoing the requested value. It also captures the child's stdout/stderr and throws with them attached when the server doesn't come up, instead of timing out into an opaque `ECONNREFUSED`. Pass `cwd` for a scratch dir with its own `.env` — `scratchCwd(prefix, contents)` / `removeScratchCwd(dir)`, exported from the same helper, make one, since server.js runs `dotenv.config()` against its cwd and would otherwise read this machine's real `backend/.env` right back over any variable the test deleted — and `env` overrides where **a key set to `undefined` deletes** that variable from the child — the "unset `DATABASE_URL`" path several of these tests exercise. Three guards in `test/helpers/spawnServer.test.js` keep that from rotting, and they fail CI rather than drifting: every `*.test.js` under `backend/` is scanned and rejected if it names a `PORT` **or** spawns `src/server.js` itself (naming a port is the symptom, spawning the entry point is the disease — a file that spawns with no `PORT` at all silently takes the hardcoded 3001 default), and `src/server.js` is checked at the source level for the `server.address().port` log, so that regression fails instantly and by name instead of as a 20-second boot timeout in every spawn-based file at once. The scans' own reach is asserted too, since a guard that walks nothing would otherwise pass forever.

**`downloadsStore` is tested as a *contract*, run twice — once per implementation** (`backend/src/services/downloadsStore.contract.js`, 0XC-110). `downloadsStore.js` ships two impls of one interface, and every other test in the repo injects `createMemoryStore()`, so before this the Postgres branch — the one production runs — had **no execution coverage at all** and a divergence in it failed nothing. The contract module registers every case against an injected `freshStore` factory: `downloadsStore.test.js` runs it against the memory impl (always, no database), and `downloadsStore.pg.test.js` runs the *same* cases against `createStore(query)`. Four things about its shape are load-bearing:

- **It skips, never fails, without `TEST_DATABASE_URL`** — `npm test` on a laptop stays hermetic and offline, and the skip carries a reason naming the variable. CI sets it (see below). Point it only at a **throwaway** database: the harness `TRUNCATE`s `downloads` and `users` between cases.
- **Setup goes through the store's own public methods** — expire with `expireForUser`, fail with `markFailed`, move with `markMoved` — so one set of lines drives both a `Map` and a table. The single exception is the injected **`backdate`**, because `created_at`/`completed_at` are `now()`-stamped by the store and no public method can move them, yet both `interval '1 ms'` clauses are exactly what needs testing. Keep that the only escape hatch; anything else a harness has to reach around the interface for is a gap in the interface.
- **It bypasses `db.js` deliberately.** That module sets `ssl` unconditionally and would refuse a plain non-TLS test container. Rather than loosen a production TLS default for a test, the pg harness builds its own `pg.Pool` with `ssl: false` and passes `pool.query.bind(pool)` into the injected-query slot `createStore` already takes — so **no production code changes**. It applies the schema via `dbInit.js`'s `applySchema`, which brings its column-drift assertion along for free.
- **A separate drift guard asserts both impls expose the same method set** (ignoring the memory impl's `_rows` escape hatch), because the contract can only call methods it already knows about — a method added to just one impl would otherwise be untested on the one that has it and absent from the other until a route hit `undefined is not a function`.

The suite was verified to have teeth by mutation rather than by inspection: breaking `USAGE_WHERE_SQL`, the `$1::uuid[]` membership test, the grace-window clause, `toApiRow`'s `Number()` coercion, `isSupersedable`, or adding a method to one impl each turns it red, and each in the matching case. One mutation initially **passed** and is worth knowing about — measuring the grace window from a bare `created_at` instead of `coalesce(completed_at, created_at)`. Catching it needs a row whose creation is old but whose completion is recent (a long download that just landed), which is the whole point of the `coalesce`; `slowButFresh` in the grace-window case is that row, so don't drop it.

**`authStore` is tested the same way** (`backend/src/services/authStore.contract.js`, 0XC-330) — same two-impl shape, same untested-SQL gap, so the same one-suite-run-twice mechanism: `authStore.test.js` against `createMemoryStore()` (always, no database), `authStore.pg.test.js` against `createStore(query)` (skips with a reason without `TEST_DATABASE_URL`), plus the same method-set drift guard. Everything above about bypassing `db.js` and reusing `applySchema` applies verbatim. Three things are specific to it:

- **There is no `backdate` escape hatch, deliberately.** `downloads`' `created_at`/`completed_at` are `now()`-stamped by the store so nothing public can move them; `login_tokens.expires_at` is a **parameter** of `insertLoginToken`, so expiry is reachable through the interface and every case sets up through public methods alone. Keep it that way — reaching around the interface here would be inventing a gap, not covering one.
- **The Postgres run gets its OWN database** (`<TEST_DATABASE_URL's name>_authstore`, created on demand), and this is not tidiness. `node --test` runs test *files* in parallel and both pg runs need a `users` table they can clear, so sharing one database makes them stomp each other in both directions — this file's `TRUNCATE … users` deletes the rows `downloadsStore.pg.test.js` just seeded (its inserts then fail `downloads_user_id_fkey`) and vice versa. Run the two files alone together on a shared database and 5–6 cases fail every time; a full `npm test` hides it only because 300+ other tests keep their windows apart. Same lesson as 0XC-275, same fix shape: take the choice away rather than coordinate. **A third pg contract run should derive its own database too**, not negotiate for the shared one. Two operational consequences: the role in `TEST_DATABASE_URL` must be allowed to `CREATE DATABASE` (the sibling is created once and left in place, truncated per case), and it is only an **unset** variable that skips — one that is set but unusable fails every case in the file.
- **The pg harness pre-warms its pool, and that is load-bearing.** The headline case is token consumption under concurrency — `consumeLoginToken`'s single atomic `UPDATE … WHERE used_at IS NULL` is what keeps a magic link single-use, and the memory impl cannot fail a test of it (single-threaded, never yields mid-consume). But a `pg.Pool` opens connections **lazily**, so firing N concurrent queries at a cold pool yields *sequential* statements: the first caller finishes both of its while the rest are still authenticating. Verified by mutation — a deliberately non-atomic read-then-write `consumeLoginToken` **passed** the concurrency case against a cold pool, and only failed (handing a session to every caller) once `freshStore` warmed `CONCURRENT_CONSUMERS` connections first. The contract owns that constant and the harness sizes off it, so they can't drift.

Verified by mutation the same way, and four of the mutants that shaped it were ones the *first* draft of the suite let through — three of them cases that read as thorough while asserting nothing (an `=` → `LIKE` rewrite of either lookup, which is an allowlist bypass; an unknown-hash case that only ran against an empty store; a `users` join nothing had a token to expose). One mutation **survives and is meant to**: widening `>` to `>=` on `expires_at`, which differs only for a token expiring in the same microsecond the query reads the clock. That is an equivalent mutant, not a gap — don't narrow the expiry margin or add a sleep chasing it (the margin is deliberately a minute; at 1ms, client/server clock skew makes the case flaky).

Both stores' drift guards are one shared assertion, `services/storeSurface.js` — they were byte-identical and kept in step by a comment asking the next person to keep them in step.

**Frontend tests are a Playwright a11y smoke suite** (`frontend/test/a11y/*.spec.js`), run with `cd frontend && npm test` (`npm run test:ui` for the Playwright UI; `npm run test:install` fetches the browser on a fresh clone). It is deliberately a handful of high-value assertions, **not** a component-unit-testing setup and not a full WCAG audit: it renders real routes in a real browser to catch the one class of defect every other gate is structurally blind to. The invisible focus ring (0XC-111) is the motivating case — `npm run lint`, `vite build` and the whole backend suite were green while the ring was invisible on every text input in the app, because nothing in CI ever rendered a page. Two files, and the reasons they're shaped the way they are:

- **`focus-ring.spec.js`** — walks the real tab order on `/login` asserting `outline-style: solid`, width ≥ 2px, offset 2px and a **non-transparent** `outline-color` on every focusable control; that last check is the one that catches this bug class, since the forms plugin's reset leaves the geometry looking perfectly healthy and only zeroes the colour. Also covers: a mouse click drawing no ring (`:focus-visible` must not fire on pointer input — asserted on a *button*, since per the CSS UI spec `:focus-visible` always matches a text field whatever the modality), and `--focus-ring` resolving in both themes with the ring's colour compared against the token rather than a hard-coded value. Its last test is a **regression guard**: it strips the `:root` prefix off the app's own rule in the live page and asserts the ring goes invisible, automating the "does this actually fail when the fix is reverted?" check that would otherwise be done by hand once and never again.
- **`aria-disabled.spec.js`** — covers the repo's aria-disabled convention (see *Styling system* below) on all three of its call sites (`UrlInput`, `FormatSelector`, `MoveToCloud`), reached through their real routes with the API stubbed. Each asserts all three halves together — marked `aria-disabled`, still keyboard-focusable, and an `aria-describedby` that resolves to non-empty text — because a dangling describedby id is the silent failure: the markup looks right and announces nothing. Note it reads the native `disabled` **IDL property** rather than using Playwright's `toBeEnabled()`, which follows the *accessibility* notion of disabled and so counts `aria-disabled="true"` as disabled — it would pass for exactly the markup the convention forbids. For the same reason, clicking an aria-disabled control to exercise its click guard needs `{ force: true }`.

**The suite is hermetic, and enforces it rather than claiming it** (`test/a11y/support/hermetic.js`): every request is intercepted, localhost passes, and anything else is aborted and recorded. The check isn't a test someone has to remember to write — `support/fixtures.js` extends Playwright's `test` with an auto-used `hermetic` fixture whose teardown fails *any* test that leaked, naming the URL (and fails a test that never called `hermetic.prepare()`, so the assertion can't go vacuous). No backend, database, or `yt-dlp` is needed; the API is stubbed per test via `hermetic.prepare({ theme, api })`. The one wrinkle is that `index.html` loads Tailwind (and its **forms plugin**) from `cdn.tailwindcss.com` at runtime, and that plugin's `:focus` reset is precisely the adversary the focus ring has to out-rank — block it and the assertions go quietly vacuous. So the CDN request is fulfilled from `frontend/test/stubs/tailwind-cdn-stub.js`, which reproduces that one rule at the specificity the CDN bundle ships it (`[type="url"]:focus` etc., `(0,2,0)`) and stubs the `tailwind` global the page's inline config block assigns to. **If the app stops loading Tailwind from the CDN, or the CDN's forms build changes shape, refresh that fixture** — a stale adversary weakens the suite without turning it red. `@playwright/test` is pinned to an exact version because it determines the browser build.

**CI (`.github/workflows/ci.yml`)** gates every PR with four parallel jobs — `lint` (root `npm run lint`), `test` (`cd backend && npm test`), `build` (`cd frontend && npm run build`), and `frontend-a11y` (`cd frontend && npm test`, the Playwright suite above) — so a failing backend test, a broken frontend build, or a focus/ARIA regression blocks the PR the same way a lint error does. CI needs no `yt-dlp`, `ffmpeg`, or network access (`backend/test/ytdlp.test.js` fakes the `yt-dlp` binary rather than spawning the real one; the a11y suite aborts any non-localhost request) — and no external service of any kind: the one database it touches is a **`postgres:16` service container** on the `test` job, brought up by the runner and thrown away with it, whose `TEST_DATABASE_URL` is what un-skips the two pg contract runs, `downloadsStore.pg.test.js` and `authStore.pg.test.js` (see the contract-test notes above — the latter creates a sibling `_authstore` database off that URL rather than sharing it). It is deliberately a container rather than a Neon branch — free, no secret, nothing to clean up, and the SQL under test uses no Neon-specific features. The service is **additive**: unset the variable and those files skip while everything else runs identically, which is what keeps a local `npm test` offline. `frontend-a11y` is the **only job that downloads a browser** — it caches `~/.cache/ms-playwright` keyed on `frontend/package-lock.json`, and still runs `playwright install --with-deps` on a cache hit because the runner's OS libraries aren't cached. `.github/workflows/deploy.yml` runs the same four checks — its `lint`/`test`/`build-frontend`/`frontend-a11y` jobs, not to be confused with its separate, pre-existing `build` job that builds the Docker image — before that image build, since `deploy.yml` also fires on the daily scheduled rebuild and on manual `workflow_dispatch`, neither of which goes through a PR.

**`backend/nodemon.json` is load-bearing — don't delete it.** Nodemon's default watch is the *entire cwd* for `.js`/`.json` changes, and the downloads directory used to sit inside that cwd (`backend/downloads/`). Since every completed job used to write `<downloadId>/metadata.json` (pre-0XC-109; today any write into a watched downloads dir would do it), the default config made **finishing a download restart the dev server** — killing the SSE stream, wiping the in-memory job registry, and dropping every in-flight request. The browser reports that dropped connection as a *CORS* error ("CORS request did not succeed. Status code: (null)"), which points nowhere near the real cause. `nodemon.json` pins the watch to `src` so downloaded media can never trigger a reload, regardless of where `DOWNLOADS_DIR` points — cheap insurance kept even now that the directory defaults outside the tree. This affects dev only — production runs `npm start` with no watcher.

**Downloads directory is configurable (`DOWNLOADS_DIR`), not hardcoded.** `backend/src/utils/storage.js` resolves it once at load time — `process.env.DOWNLOADS_DIR` if set, else the historical `backend/downloads` — to an absolute path, and every consumer (routes, the cleanup sweep, tests) imports that single `downloadsDir` rather than joining a path itself. `server.js` logs the resolved path once at startup (`📁 Downloads directory: …`). This exists because runtime media living inside the linted, watched, packaged source tree kept causing trouble beyond the nodemon restart above — linters/formatters/editor indexing all had to be told to skip a directory that can hold many gigabytes of video, and the Docker image's bind mount only worked by convention. `docker-compose.yml` and the `Dockerfile` both set `DOWNLOADS_DIR=/data/downloads` explicitly (outside `/app/backend`) rather than relying on the default.

**Single-server mode:** if `frontend/dist/` exists, `backend` serves it statically with an SPA fallback (see `server.js`). So `cd frontend && npm run build` then `cd backend && npm start` serves the whole app on port 3001 with no separate frontend process. This is how production runs.

## Architecture

**Tubekeep** — a yt-dlp-backed video/audio downloader. React SPA (Vite, port 5173 in dev) + Express API (port 3001) + the `yt-dlp` CLI. Downloads land in `<DOWNLOADS_DIR>/<downloadId>/` (`DOWNLOADS_DIR`, default `backend/downloads/`) and are *expired* (not hard-deleted) after `MAX_FILE_AGE_HOURS` (**1h**, `services/cleanup.js`).

### Download flow
1. `GET /api/info?url=...` → `services/ytdlp.js` runs `yt-dlp --dump-json`, returns formats grouped into `{ video, audio, combined }`.
2. `POST /api/download` → mints a `downloadId` (a UUID) **and starts the download job** server-side via the download manager. The parameters ride the **request body** (`url`, `formatId`, `type`, `title`, `thumbnail`, `keep`, `filesize`). The job runs yt-dlp to completion **independent of any client connection** — navigating away no longer aborts it. Three guards run here, all before any job starts, in this order: (1) the client-passed `filesize` against the **per-user quota** (`hasQuotaFor` over `store.usageForUser`) → **HTTP 507**; (2) the same size against the **global disk** fit margin (`hasRoomFor`) → **HTTP 507** too; (3) the concurrency cap, which `startJob` throws (`DownloadCapError`) → **HTTP 429**. All are `{ success: false, error }` the UI surfaces inline. Between (2) and (3) the download is **recorded in the `downloads` table** under the requesting user (as `status: 'downloading'`), so an in-flight download survives a reload — a cap rejection therefore deletes that row again before returning 429, and a failed insert aborts the start with a 500. The job's terminal hooks (`onComplete`/`onError`, injected into `startJob`) flip the row to `complete` (writing the real filename + on-disk size) or `failed`.
3. `GET /api/download/progress/:downloadId` → **pure observer SSE.** It looks the job up in the registry, replays current progress, and streams `progress` / `complete` / `error` events plus `ping` heartbeats every 15s (for proxy keep-alive). It **does not spawn a process**; disconnecting only unsubscribes (the job keeps running). Reconnecting (reload / new tab / cold visit) **attaches** to the in-flight job — no second process, no query params needed. An unknown id (e.g. after a server restart) yields a terminal `"download not found"` error.
4. `DELETE /api/download/:downloadId` → **explicit cancel.** Aborts the running job (via its `AbortController`), removes its partial files/directory, and drops the caller's history row (`store.deleteForUser`, so another user's id reads as 404) — a cancelled download must not linger in the list or against the quota. Succeeds if *either* half found something; 404 only when neither did. Wired to the `DownloadingCard` **Dismiss** and the download page **Cancel**.
5. `GET /api/files/:downloadId/:filename` → serves the file with HTTP range support (in-browser seeking/streaming) and RFC 5987 `Content-Disposition` for unicode filenames. `?action=download` forces an attachment.

**Download manager (`services/downloadManager.js`)** — an in-memory `Map<downloadId, job>` registry. Each job holds `{ status: 'running'|'complete'|'error', progress, result, error, params, hooks, emitter, abortController }`. Observers attach through `subscribe(downloadId, { onProgress, onComplete, onError })`, which atomically replays the job's current/terminal state and then streams live events (returning an unsubscribe fn, or `null` for an unknown id) — the `emitter` stays internal so the observer route is a thin SSE serializer. On completion the job builds the result payload for the SSE `complete` event and awaits `hooks.onComplete` (which persists the real filename + size to the user's `downloads` row — the **only** lifecycle record; nothing is written to disk) **before** emitting `complete`, so a client that reloads the instant it sees the event reads a matching row. Hook failures are caught and logged (`runHook`): a DB blip must never turn a finished download into a failed one. **In-memory only** — an in-flight download dies on server restart (a reconnect then gets "download not found"); terminal jobs are retained ~30 min for late reconnects, then pruned by the hourly cleanup sweep (`sweepJobs`). The concurrency cap is `MAX_CONCURRENT_DOWNLOADS` (default **3**) simultaneously-running jobs. `runningDownloadIds()` exposes the ids of jobs currently `running` in this process — the cleanup sweep's precise "don't touch this directory, it's being written to right now" signal (see below).

**Storage guards (`GET /api/disk`, `routes/disk.js`)** — two independent limits, both enforced at `POST /api/download` and both surfaced to the format screen by one endpoint. The response is `{ total, free, used, sizeMultiplier, headroomBytes, quota: { used, max, remaining } }`.

- **Global free disk** (server housekeeping): `hasRoomFor(free, filesize)` — `free >= filesize * DISK_SIZE_MULTIPLIER (2×) + DISK_HEADROOM_BYTES (500 MB)`. The `2×` covers the transient video+audio merge.
- **Per-user quota** (the user's allowance): `hasQuotaFor(used, max, filesize)` — `used + filesize <= max`, where `max` is the `users.max_storage_bytes` column (default 5 GB, **`-1` = unlimited**) and `used` is `SUM(filesize)` of that user's live rows (`NOT expired AND NOT moved AND status <> 'failed'` — an in-flight `downloading` row counts, so parallel starts can't race past the cap). **No** multiplier/headroom here: the quota counts what a download *keeps*, not its merge footprint.

Both live in `utils/storage.js` and the frontend reads the same knobs + quota numbers back out of the `/api/disk` response (`hasRoomFor` / `hasQuotaFor` / `downloadBlockReason` in `lib/media.js`), so client disable-check and server backstop can't drift — the client's `hasQuotaFor` consumes the response's `quota.remaining` rather than re-deriving it from `used`/`max`, so the clamp-at-zero and the `-1` unlimited sentinel are defined once, on the server. `FormatSelector` shows a **"Your storage"** banner (used / left, or "unlimited") and disables any format either guard rejects, with the reason under it. Unknown-size formats are never blocked by either. The client-passed `filesize` is untrusted (a UX guard, not a security boundary) — the row's size is corrected to the real one on completion. The two guards fail differently on error: the quota check **fails closed** (a DB outage must not hand out free storage), the disk check **fails open**.

### yt-dlp integration (`services/ytdlp.js`) — read before touching downloads
This file carries deliberate workarounds for YouTube's 2026-era extraction breakage. Do not "simplify" them away:
- **`YOUTUBE_EXTRACTOR_ARGS = 'youtube:player_client=android_vr;formats=missing_pot'`** is passed to *every* yt-dlp invocation. The default web/tv clients require a JS challenge solver that's broken in yt-dlp 2026.02.x (yields only a single 360p format and hangs). `android_vr` restores the full 144p→4K ladder; `formats=missing_pot` keeps formats whose URLs lack a PO Token. Namespaced under `youtube:` so other extractors are unaffected.
- **SABR retries.** YouTube's per-session SABR experiment intermittently strips format URLs. `getVideoInfo` retries the metadata fetch up to 4× with back-off until video-only formats appear. `downloadVideo`/`downloadAudio` retry up to 3× on `Requested format is not available|SABR|missing a URL`, and use fallback format strings (e.g. `${formatId}+bestaudio/bestvideo+bestaudio/best`) so a vanished exact format still resolves to *something*.
- **Binary & PATH.** Prefers `~/.local/bin/yt-dlp` over the system one, and injects Node's dir into `PATH` because yt-dlp's SABR challenge solver shells out to `node`.
- **Black-holed IPv6, auto-detected at boot (`services/ipv6.js`, 0XC-126).** On a network whose router advertises an IPv6 default route while IPv6 traffic is actually black-holed, yt-dlp takes **~85s per call instead of ~1.5s** — Python's urllib has no Happy Eyeballs, so it waits out the full TCP timeout on each AAAA address before falling back to IPv4. Symptom: `/api/info` spins for a minute-plus and downloads crawl, with near-zero CPU. `server.js`'s boot sequence runs `ensureIpv4Decision()` (which calls `decideForceIpv4()`) alongside `ensureSchema()`, before `app.listen`: `decideForceIpv4` attempts one IPv6 TCP connect to a reliable public host (Google Public DNS, port 53) with a ~2s timeout (`probeIpv6Reachability`) and classifies the outcome — connects → `'reachable'` (leave IPv4-forcing off), the OS rejects it immediately → `'no-route'` (an ordinary IPv4-only machine; also left off), neither happens before the timeout → `'blackholed'` (a route exists but packets vanish — exactly this failure mode), which logs a warning and returns `true`. `ensureIpv4Decision` then feeds that decision into `ytdlp.js`'s `setForceIpv4`, so every subsequent call prepends `--force-ipv4`. The probe is **skipped** in the test suite (`NODE_ENV=test`, mirroring `ensureSchema`'s `DATABASE_URL` skip) so the hermetic suite still reaches no real network, and it's injectable (`probe`/`connect` params) so `ipv6.test.js` covers all four outcomes without touching a socket. **`YTDLP_FORCE_IPV4`** now overrides the probe rather than being the primary switch — set explicitly (`true`/`false`) only to force a direction by hand; unset defers to the boot probe. Diagnose the underlying condition with `curl -6 -m 5 https://www.youtube.com` (hangs) vs `curl -4` (fast).
- Video+audio (`type: 'video'`) merges to mp4 via `--merge-output-format mp4`; `type: 'combined'` downloads a pre-merged format as-is; `type: 'audio'` pulls bestaudio.

### Expire vs. delete (two-tier lifecycle)
A download is **"expired"** when its history row survives but the media files are gone. This keeps the row visible so it can be re-downloaded. The `downloads` row is the **single** lifecycle record (0XC-109) — there is no on-disk mirror; a download directory holds only its media files, and the filesystem layer (`utils/storage.js`) only ever answers "does this directory exist, and what files (and how recently touched) does it have" (`getDownloadDir`/`listDownloadDirs`). The **`downloads.expired` column is what the UI reads**. Two distinct destructive operations, both via `DELETE /api/files/:downloadId`, each touching the row *and* the disk:
- default → `store.expireForUser` + `expireDownload()`: removes the whole directory, flags the row `expired` + stamps `expired_at`.
- `?permanent=true` → `store.deleteForUser` + `deleteDownload()`: removes the row and the whole directory.

At the filesystem level expire and permanent-delete are now the same operation (`expireDownload`/`markMoved` both delegate to `deleteDownload`) — the distinction between "expired" (row survives) and "deleted" (row gone) is purely a `downloads`-table concept; nothing on disk needs to represent it.

Both routes are scoped to the caller's own rows — `store.expireForUser`/`deleteForUser` carry the `user_id` in their `WHERE`, so another user's id simply reads as `404`.

The hourly cleanup scheduler (`services/cleanup.js`, `MAX_FILE_AGE_HOURS` = **1**) *expires* old downloads — it does not hard-delete. `cleanupOldDownloads` ages a directory off its **mtime** (there's no stored `createdAt` to read) and skips two things regardless of age: any id in `runningDownloadIds()` (a job this process is actively writing to — see the download manager note above) and, when a store is available, every id in `store.keptIds()` (downloads flagged `kept`, since that flag now lives only in Postgres). **Reading `keptIds()` fails closed, not open**: if the query throws, `runCleanup` skips age-based expiry entirely for that sweep pass — not just for potentially-kept ids — rather than proceeding with an incomplete skip-set. Deleting a `kept` download's media is irreversible; delaying a disk reclaim by an hour is not, so an unreachable-DB blip costs a skipped pass rather than a silent, permanent loss of something a user pinned (same reasoning as the per-user quota check's fail-closed behavior above). It then reconciles the `downloads` table against the filesystem: first, any `downloading` row whose directory already holds finished media — files present, none of them yt-dlp partial artifacts (`.part`/`.ytdl`), and the job not running in this process — is reconciled to `complete` from the real on-disk file (`store.markComplete(id, patch, { onlyIfDownloading: true })`), picking the largest file exactly as the download flow's `describeDownloadedFile` does. This covers a completion hook whose DB write was lost (e.g. a transient error) even though the download itself succeeded (0XC-120; with `metadata.json` gone, "finished" is detected from the directory contents themselves). This step runs **before** the other two, so a row that would otherwise qualify for both is corrected, not wrongly failed; it first calls `store.downloadingIds()` to narrow to the (normally empty) set of rows actually still `downloading`, so a healthy sweep doesn't stat and update every live download on disk. Then `expireMissing` marks any completed, live row whose media is gone as expired (no matter who removed it), and `failStale` retires rows genuinely stranded `downloading` by a restart (6h window) — so none of the three can occupy a user's quota forever. All reconcile steps need the store, which `server.js` passes in (`startCleanupScheduler({ store })`) — so the standalone `npm run cleanup` CLI, which passes none, is **filesystem-only**: it still expires by directory age, but with no store it can't read `keptIds()`, so a `kept` download run through the CLI alone (never through the live server) isn't protected — a known, accepted limitation of that fallback tool, not of the running server. The CLI also has no job registry of its own — it's always a separate one-shot process from any running server, so `runningDownloadIds()` (which only knows about jobs in *its* process) can't protect an in-progress download either — so its age threshold is the wider `STALE_DOWNLOADING_MS` (6h, the same margin the old dedicated orphan-directory sweep used), not the server sweep's tight `MAX_FILE_AGE_HOURS` (1h); the tight window is only safe for the server sweep because it has `runningDownloadIds()` to fall back on. The sweep scans the downloads directory once (`listDownloadDirs()`) and hands that snapshot to `cleanupOldDownloads`, deriving "still on disk" from it rather than walking the tree a second time. The frontend holds the two lists (active + expired) in memory only — they are re-read from the server, **not** localStorage.

**Re-download dedupe — one row per canonical video identity (0XC-10, refined by 0XC-117):** when a download **completes**, the user's older rows for the same video are hard-deleted (row + media), so a re-download *replaces* the stale entry instead of sitting beside it and the old copy stops occupying the quota. Two states are spared: **moved-to-cloud** rows (the media lives in the user's own cloud and the row still carries the "Open in …" link) and **`downloading`** rows (a concurrent job for the same video, which deleting would orphan). Expired, failed and live completed rows all go.

This rule is **server-side**, in the download job's `onComplete` hook (`supersedeOlderRows` in `routes/download.js` over `store.supersedeForUser`) — *not* in the browser. It originally lived in `addDownload` and only ran if a tab happened to witness the SSE `complete` event; since downloads finish server-side regardless of the client (0XC-25/0XC-26), leaving the download page is the normal flow, so the dedupe silently never ran and both rows came back on the next sync. Running it in the completion hook is also what makes "only supersede once the new download actually lands" true: an abandoned or failed re-download leaves the old row intact. `supersededBy` in `HistoryContext.jsx` mirrors the same predicate purely so the list updates instantly — it issues **no** requests, and its spared cases must stay in step with `SUPERSEDABLE_SQL` / `isSupersedable` in `downloadsStore.js`.

Matching used to be exact string equality on the stored `url`, so the Redownload button (which round-trips the URL verbatim) always matched but a hand-pasted variant (`youtu.be/…`, `&t=`, `&si=…`) didn't (0XC-117's original bug). The match key is now the namespaced extractor id — `source_key`, e.g. `youtube:dQw4w9WgXcQ` (`extractor:info.id` from yt-dlp, built in `services/ytdlp.js`'s `getVideoInfo` and surfaced as `sourceKey` in the `/api/info` response) — stable across every URL form the same video can be pasted as, and namespaced so two extractors can't collide on the same bare id. The client carries it from `/api/info` through `POST /api/download`'s body untouched (untrusted input, like `filesize` — validated for shape/length in `routes/download.js`'s `isValidSourceKey`, never trusted as a security boundary, since `supersedeForUser` stays scoped by `userId` regardless). `supersedeForUser` (and its JS mirror `sharesSource`, both in `downloadsStore.js`) matches on `source_key` **only when both the fresh download and the candidate row have one**; whenever either side lacks a key — a row from before this column existed, or an extractor that returned no id — it falls back to the original exact-`url` match, so nothing regresses. The completion payload threads `sourceKey` through `downloadManager.js`'s `job.result` too, so the frontend's instant `supersededBy` mirror agrees with the server the moment the SSE `complete` event lands, not just after the next reload.

**Pending/failed rows:** downloads run server-side and finish even if the user leaves the download page, so history rows are written **at click time**, not on SSE completion. `handleDownload` (`InfoPage.jsx`) calls `startPending()` to put a `status: 'downloading'` row into the in-memory history list immediately — the server already inserted the real row, this just avoids waiting for a re-sync (fields: `downloadId`, `url`, `type`, `title`, `thumbnail`, `createdAt` — no `filename`/`size` yet). On SSE `complete`, `addDownload(data.data)` replaces it in place with the full completed record (which carries **no** `status`), so it renders as a normal `ActiveCard`. On SSE `error`, `markFailed()` flips it to `status: 'failed'`. `DownloadsPage` routes `status === 'downloading'` → `DownloadingCard` (spinner, links to `/download/:id`, plus a **Dismiss**) and `status === 'failed'` → `FailedCard` (Redownload + Dismiss) **before** the `ActiveCard` fallback. These rows exist **server-side too** (the `POST` inserts them), so a reload re-reads them from the DB — no client-side preservation needed. The two Dismisses differ: a **downloading** row uses `cancelDownload()` — the job runs server-side regardless of the client, so dismissing it must `DELETE /api/download/:id` to actually stop the job (abort + remove partials), which also deletes its history row; a **failed** row uses `dismissFailed()`, a hard-delete (`DELETE /api/files/:id?permanent=true`) rather than a move to the expired list, since its file may never have landed.

### Cloud upload ("Move to cloud")

Once a download completes, a visitor can **move** it into their own Dropbox, Google Drive, or OneDrive instead of downloading it to their device: upload to the visitor's cloud, then drop the local copy. "Moved" is a **third terminal state** alongside expired/deleted (see "Expire vs. delete" above) — a moved row keeps its history card (source `url` + a link into the visitor's cloud) but its media is gone, removed by the same directory-deleting call `expireDownload` uses (`utils/storage.js`'s `markMoved`, which since 0XC-109 simply delegates to `deleteDownload`; "moved" lives purely in the `downloads` row's `moved`/`moved_info` columns, since there is no on-disk lifecycle record left to patch). It also stops counting toward the owner's quota — `downloadsStore.js`'s `USAGE_WHERE_SQL`/`countsTowardUsage` exclude `moved` rows the same way they exclude expired ones. This supersedes `docs/cloud-upload-design.md`'s original "Model A" (hard-delete the whole directory on move, `/play/:id` stops working) — that document is now a historical design record; this section describes what actually shipped.

**Provider registry & contract (`backend/src/services/cloud/`).** `index.js`'s `getProvider(name)` / `listEnabledProviders()` are the only way routes or the job manager reach a provider — nothing imports `dropbox.js`/`googledrive.js`/`onedrive.js` directly, which is what let OneDrive (0XC-13) slot in behind the same shape without touching the routes, the job manager, or the UI. A `CloudProvider` implements five functions: `isEnabled()` (all its required env vars are set), `getPublicConfig()` (the non-secret `{ clientId, redirectUri }` the frontend may read), `exchangeCode({ code, codeVerifier, redirectUri })` (authorization-code → tokens), `refresh({ refreshToken })` (refresh-token → a fresh access token), and `upload({ accessToken, filePath, fileName, size, onProgress, signal })` (stream the file from disk, return `{ path, name, link }`). `shared.js` hoists what both providers used to duplicate (0XC-93): the `CloudError` type (a `code` plus optional `status`), the OAuth `postToken` relay POST, the `refresh` shell, `withRetry` (retries only 5xx/network failures — auth and quota errors are terminal, and a cancelled upload throws a classified `aborted` `CloudError` instead of looking transient), the shared 8 MB `DEFAULT_CHUNK_SIZE`, and `makeProgressReporter`. Every provider publishes `clientId` from `getPublicConfig` (unified there in 0XC-93 — Dropbox used to publish `appKey`, which the frontend had to map around). Dropbox (`dropbox.js`) uses the official `dropbox` SDK for chunked upload sessions above the 8 MB single-shot threshold and builds the "Open in Dropbox" link as a no-scope path-based web deep link into `/Apps/<DROPBOX_APP_FOLDER>/`. Google Drive (`googledrive.js`) hand-rolls the same shape against Drive's resumable-upload REST API (raw `fetch`, no SDK), scoped to `drive.file` (app-created files only, so it never needs Google's sensitive-scope review) and finds-or-creates a `GOOGLE_DRIVE_FOLDER` folder in the visitor's My Drive. OneDrive (`onedrive.js`, 0XC-13) does the same against Microsoft Graph's resumable-upload API, and is the one provider registered as a **public client** — it has no app secret at all (`MS_CLIENT_ID` + `MS_REDIRECT_URI` only), relying on PKCE alone, and its `Files.ReadWrite.AppFolder` scope confines every upload to the app's special folder (`/me/drive/special/approot`) rather than the whole drive; the `common` authority accepts both personal Microsoft accounts and work/school Entra ID ones. No provider persists anything — an access token lives only for the life of one upload job.

**Routes & job manager.** `routes/cloud.js`'s `createCloudRouter({ store })` mounts at `/api/cloud`: `GET /providers` (public config for enabled providers only — how the frontend hides "Move to cloud" entirely when none are configured), `POST /oauth/token` / `POST /oauth/refresh` (the stateless PKCE relay — the app secret, for the providers that have one, never leaves the server; tokens are handed back to the browser and nothing is persisted server-side), `POST /upload` (checks `store.findForUser` so only the download's owner can move it — the id alone would otherwise let one signed-in user copy another's file into their own cloud — then hands off to `services/cloud/jobs.js`'s `createJob`, returning only an opaque `jobId`), and `GET /upload/:jobId/progress` (SSE — the URL carries just the `jobId`; this is why the access token rides the `POST /upload` body instead of a query string, the same token-leak-safe-transport concern `docs/cloud-upload-design.md` called out). `jobs.js` is an in-memory job registry shaped like the download manager: `MAX_CONCURRENT` (3) simultaneous uploads with the rest queued, a hard TTL (30m) that aborts and fails an abandoned job, and a short linger (2m) after a job settles so a reconnecting SSE client can still read the outcome. On success it calls `markMoved()` (the media directory removed) and best-effort mirrors the same flag onto the caller's `downloads` row via the injected `store` — a DB blip here must not fail an upload that already succeeded, mirroring `downloadManager.js`'s `runHook` philosophy. Disconnecting the SSE stream does **not** abort the upload (a move is a server→cloud transfer meant to survive the tab closing); only the job's own hard TTL or a genuine provider failure can.

**Frontend.** `lib/cloud.js` is provider-agnostic, data-driven by one `PROVIDERS` table (Dropbox, Google Drive, OneDrive): it runs the PKCE flow (Web Crypto `S256` challenge), opens the consent popup, and keeps each provider's tokens in `sessionStorage` only (dies with the tab, matching the design doc's browser-is-system-of-record-for-credentials model) — `getFreshAccessToken(name)` transparently refreshes via the backend relay when a token is near expiry and throws a `NOT_CONNECTED`-coded error otherwise so callers know to prompt a (re)connect. `pages/OAuthCallbackPage.jsx` is the `/oauth/callback` route the popup lands on — a standalone route outside the `App` shell whose only job is relaying `{ code, state }` back to the opener via `postMessage` (targeted at the exact origin) and closing itself. `hooks/useCloudMove.js` drives one download's move end to end — lazy connect → `POST /api/cloud/upload` → SSE progress by `jobId` → on completion, flags the row moved in `HistoryContext` — through a `phase` state machine (`idle | connecting | starting | queued | uploading | complete | error`). `components/MoveToCloud.jsx` is the button/menu/progress UI built on that hook: hidden until the enabled-providers list resolves (avoids a flash-then-disappear) and when none are configured, disabled with an "Expiring soon" nudge once a file's remaining runway drops under 15 minutes (so a move can't be started only to have the source file expire mid-upload), and on failure offers a "download instead" fallback alongside "Try again". Since 0XC-11 it renders in **both** `DownloadsPage` (the active-download list) and `VideoPlayer` (the `/play/:id` playback view) — not only the downloads history — so a visitor can move a file to their cloud from wherever they're already looking at it.

The `DROPBOX_*` / `GOOGLE_*` / `MS_*` env vars are listed in **Environment Variables** below; each provider is independent, and a provider missing any of its required vars is cleanly omitted from `listEnabledProviders()` rather than erroring. To add a **new** provider: implement the five `CloudProvider` functions in a new `services/cloud/<name>.js` (reusing `shared.js`), register it in `services/cloud/index.js`'s `PROVIDERS` map, and add its metadata (`label`, `icon`, `authEndpoint`, `scopes`, optional `authParams`/`configKey`, `viteClientId`, `viteRedirect`) to `lib/cloud.js`'s `PROVIDERS` table — nothing else in `routes/cloud.js`, `jobs.js`, `useCloudMove.js`, or `MoveToCloud.jsx` needs to change. OneDrive (0XC-13) is the worked example: it landed as exactly those three edits plus `docs/onedrive-setup.md`.

### Backend (`backend/src/`)
- **`server.js`** — Express entry (helmet with CSP disabled for media + cross-origin resource policy, CORS, morgan), route mounting, static SPA serving, cleanup scheduler bootstrap. Sets `app.set('trust proxy', 1)` — production sits behind exactly one hop (Cloudflare straight into the container; no nginx/Caddy in front, see Deployment) — so `req.ip` reflects the real visitor instead of Cloudflare's own edge address (0XC-128). Don't bump this to `true`: that trusts every hop in a client-supplied `X-Forwarded-For` chain, letting a client mint unlimited rate-limit buckets by forging extra entries.
- **`utils/rateLimit.js`** — the in-memory sliding-window limiter mounted per-route in `server.js`. Keys each bucket on `CF-Connecting-IP` when present (Cloudflare overwrites this at its edge) and falls back to `req.ip` otherwise — local dev and any deploy not behind Cloudflare still bucket correctly off `trust proxy` above. **Neither header is authenticated by this code** — both are only trustworthy to the extent the deployment actually guarantees every request transits Cloudflare first. `docker-compose.yml` publishes the app's port directly and nothing in this repo enforces that guarantee at the network level (no firewall/security-group scoping it to Cloudflare's ranges), so a request that reaches the origin by another path can forge either header and mint unlimited rate-limit buckets. Closing that gap is an infrastructure change (bind the port to loopback behind a Cloudflare Tunnel, or firewall it to Cloudflare's published IP ranges), tracked separately — see the 0XC-128 follow-up.
- **`routes/`** — thin HTTP layer: `info.js`, `download.js` (start job / observer SSE / cancel), `files.js` (range serving + public per-item metadata + per-user list + expire/delete), `disk.js` (`GET /api/disk` — disk usage + fit knobs + the caller's quota), `cloud.js` (OAuth + move-to-cloud; uses the store only to confirm the caller owns the download). Every router except `info.js` is a **factory** — `createDownloadRouter`/`createDiskRouter`/`createCloudRouter` take `{ store }` and `createFilesRouter(requireAuth, { store })` — taking the injected `downloadsStore`, so they unit-test against `createMemoryStore()` without Postgres. (`auth.js` follows the same pattern over `authStore`.)
- **`services/ytdlp.js`** — all subprocess spawning (see above).
- **`services/ipv6.js`** — the boot-time black-holed-IPv6 probe + decision logic (see above); `server.js` calls it once at boot and feeds the result into `ytdlp.js`'s `setForceIpv4`.
- **`services/downloadManager.js`** — in-memory job registry that runs downloads to completion decoupled from the client SSE; enforces `MAX_CONCURRENT_DOWNLOADS` (see Download flow). Takes no database dependency — the caller injects `{ onComplete, onError }` hooks into `startJob` to persist the terminal outcome.
- **`services/cleanup.js`** — hourly scheduler; also runnable standalone (`npm run cleanup`, filesystem-only — no store is registered in that process). Also prunes finished download-job records (`sweepJobs`) and reconciles the `downloads` table (`markComplete` with `onlyIfDownloading` / `expireMissing` / `failStale`, in that order).
- **`utils/storage.js`** — the source of truth for the directory layout: `getDownloadDir`/`listDownloadDirs` (filesystem-only reads — files + mtime, no lifecycle data), `expireDownload`/`markMoved`/`deleteDownload` (all remove a whole directory), `cleanupOldDownloads` (the mtime-based age sweep), and both storage guards (`getDiskUsage`/`hasRoomFor` + the fit constants; `hasQuotaFor`/`remainingQuota` + `UNLIMITED_QUOTA`).
- **`services/downloadsStore.js`** — data access for the `downloads` table (per-user history + quota usage), same shape as `authStore`: `createStore(query)` for production, `createMemoryStore()` for tests. `toApiRow` is the single place DB columns become the API/UI contract, and `USAGE_WHERE_SQL` / `countsTowardUsage` are the one quota-usage rule written for each impl (keep them adjacent — they must change together; adjacency helps a reader but does nothing to stop drift, which is what the contract suite above is for — **change one impl and the other's run of the same cases goes red**). The **background workers** that run outside any request (the cleanup sweep, the cloud-move job) take the store as an argument from the caller that already holds it (`startCleanupScheduler({ store })`, `createJob({ …, store })`) rather than reaching for a module singleton; omitted in unit tests, where those paths no-op.
- **`utils/friendlyError.js`** — `friendlyYtDlpError(rawMessage)`: maps raw yt-dlp stderr to short, blame-free user copy via an ordered `{ pattern, message }` list (unavailable/removed, private, members-only, age-restricted, geo-blocked, live/premiere, unsupported URL, network/timeout), falling back to a generic message. Matches lowercased substrings anywhere in multi-line stderr, most-specific first. `getVideoInfo`'s catch and `downloadManager`'s `runJob` error path both run every user-facing error through it, so `/api/info` and SSE `error` never leak exit codes, extractor tags, or enforcement-vendor names. The **full raw stderr is still `console.error`-logged** server-side for operators — only the user-facing string is rewritten.

### Auth + database (magic-link login)
Only emails present in a **manually-managed** Neon `users` table can log in — there is **no signup and no admin UI**; add/remove a user or change their quota by editing the `users` row in the Neon dashboard. Login is an emailed single-use magic link → a JWT httpOnly cookie session.

- **`db.js`** — lazily-created `pg` connection pool over `DATABASE_URL` (forces TLS). Exposes `query(text, params)` and `getPool()`. Importing it never connects, so tests that inject their own store don't need a database.
- **`schema.sql`** + **`npm run db:init`** (`src/dbInit.js`) — hand-written schema (no ORM/migrations). Defines `users` (id, email UNIQUE, name, `max_storage_bytes` bigint default 5 GB / `-1` = unlimited), `login_tokens` (stores only the SHA-256 **hash** of each token, single-use + ~15-min expiry), and `downloads` (the per-user download history: lifecycle `status`/`expired`/`moved`+`moved_info`/`kept`, the `filesize` the quota sums, and the nullable `source_key` used to match re-downloads by canonical video identity — 0XC-117). Idempotent — safe to re-run. `dbInit.js` exports the applier as `applySchema(pool)`; `npm run db:init` is a thin CLI over the same function. **`server.js` also awaits `applySchema()` on every boot** when `DATABASE_URL` is set (skipped otherwise, e.g. unit tests), then asserts every column `schema.sql` defines is present — so a database that's missing a column a later commit added self-heals with no manual step (0XC-115). That required set is **parsed out of `schema.sql` itself** by `src/schemaColumns.js` (`CREATE TABLE` bodies + `ALTER TABLE ADD COLUMN` statements), not a hand-maintained list — it used to be a `REQUIRED_COLUMNS` allowlist that only covered `downloads`' four most load-bearing columns, so the assertion now automatically covers every table (`users`, `login_tokens`, `downloads`) instead of just the ones someone remembered to hardcode (0XC-129). A failed apply or a failed column assertion is fatal in production (`process.exit(1)`, mirroring the `JWT_SECRET` boot check below) and a loud warning in development. `npm run db:init` still works standalone for provisioning a fresh Neon database by hand.
- **`services/mailer.js`** — `sendMagicLink(email, rawToken)`. Sends via the **Resend** HTTP API when `RESEND_API_KEY` is set; otherwise (dev/tests) **logs the link to the server console** so the flow is testable without credentials. Builds links from `APP_URL`, sends from `EMAIL_FROM`. Never throws to the caller (a mail outage must not leak whether an address was allowed) — but it does **log** Resend's `{ data, error }` rejection (status + message), because the SDK resolves rather than throws on an API refusal and an unchecked `await` would swallow every delivery failure silently.
- **`EMAIL_FROM`'s domain must be Verified in Resend, and this is the repo's most expensive footgun** — an unverified domain means Resend rejects **every** send, so login breaks for *all* users at once rather than degrading. Two failure modes make it hard to spot, and both have hit this deploy. First, the `Tubekeep <onboarding@resend.dev>` fallback (used only when `EMAIL_FROM` is unset) delivers to the **Resend account owner's address alone**, so an owner logging in successfully proves nothing about anyone else. Second, verification runs on DNS records Resend issues — a DKIM `TXT` at `resend._domainkey`, an SPF `TXT` and an `MX` on a send subdomain — and on Cloudflare **every one of them must be DNS-only (grey cloud)**; a proxied record answers with Cloudflare's IPs instead of the published value and verification silently never passes, with nothing naming the cause. Proxying the apex for the web app is correct and unrelated. Check the live state with `dig TXT resend._domainkey.<domain>` (must be non-empty), `dig TXT send.<domain>` and `dig MX send.<domain>`, and read the container logs for the rejection `mailer.js` surfaces before looking anywhere else. Production's value comes from `/opt/tubekeep/.env` on the Docker host via `env_file` in `docker-compose.yml`, so changing it needs a `docker compose up -d`.
- **`services/authService.js`** — Express/Postgres-free crypto + orchestration (so it unit-tests in isolation): token `generate`/`hash`, JWT `signSession`/`verifySession` (reads `JWT_SECRET`, 30-day expiry), and `requestMagicLink`/`verifyMagicLink`. Token consumption is a single atomic `UPDATE … WHERE used_at IS NULL AND expires_at > now()` in the store, which is what enforces single-use even under concurrent clicks.
- **`services/authStore.js`** — data access behind a small interface. `createStore(query)` is the Postgres-backed impl; `createMemoryStore()` implements the same four methods in memory for tests. Routes/middleware take a store so nothing touches Postgres in unit tests. Both impls are held to one contract suite (see the testing note above) — **change one and the other's run of the same cases goes red**.
- **`routes/auth.js`** — `createAuthRouter({ store, mailer })`. `POST /api/auth/request` (rate-limited; **generic response regardless of allowlist**), `GET /api/auth/verify?token=…` (consume token → set cookie → redirect to `APP_URL/?login=success|error`), `POST /api/auth/logout` (clear cookie), `GET /api/auth/me` (session user or 401). Cookie flags: httpOnly + SameSite=Lax always, Secure only in prod.
- **`middleware/requireAuth.js`** — `createRequireAuth(store)` verifies the session cookie JWT, loads the user, and attaches `req.user` (incl. `user_id` for 0XC-100); 401 otherwise. Mounted on **every** API router (`/api/info`, `/api/download`, `/api/disk`, `/api/cloud`, and `/api/files`'s list/PATCH/DELETE) **except** the public `GET /api/files/:downloadId/:filename` serve route, so shared `/play/:id` links keep working for logged-out visitors. CORS runs with `credentials: true` against the **pinned** `FRONTEND_URL` (never a wildcard).
- **Deploy ordering** — because every API route now requires a session, this backend must ship **together with or after** the frontend login UI (0XC-98). Deploying it ahead of 0XC-98 would 401 the existing SPA (which sends no session cookie yet) and lock users out. `db.js` verifies the DB's TLS cert by default (`DATABASE_SSL_NO_VERIFY=true` opts out); the server refuses to boot in production without `JWT_SECRET`.

### Frontend (`frontend/src/`)
Routing-based, **not** a single mega-component (the old `App.jsx`-holds-all-state model is gone):
- **`main.jsx`** — `createBrowserRouter` defines routes; `<AuthProvider>` wraps `<HistoryProvider>` wraps `<PlayerProvider>` wraps the router so auth, history, and player state are all global. `/login` and `/oauth/callback` are standalone (outside the `App` shell); everything under `/` is in the shell, with the public `play/:downloadId` declared **before** the `<ProtectedRoute>` layout route that gates the rest.
- **`App.jsx`** — layout shell only (header/nav + `<Outlet/>`). The header shows the logged-in user's `name` (falling back to email) + a **Logout** button (`logout()` → `/login`), or a **Log in** link when signed out (so anonymous `/play/:id` visitors can still reach login).
- **`components/ProtectedRoute.jsx`** — the login gate. Renders `<Outlet/>` for authed users, redirects the rest to `/login`. It also absorbs the magic-link landing: the backend's `GET /api/auth/verify` 302s to `/?login=success|error`, so `ProtectedRoute` strips `?login=success` once the session is loaded, and on `?login=error` (or any anonymous visit) redirects to `/login` carrying `state.linkError` so the login page explains the expired/invalid link.
- **`pages/`** — `LoginPage` (`/login`, email → `POST /api/auth/request` → generic "check your inbox" confirmation; no signup/password), `HomePage` (URL input → navigates to `/info?url=`), `InfoPage` (format selection), `DownloadPage` (`/download/:id`, runs the SSE), `DownloadsPage` (active + expired lists), `PlayPage` (`/play/:id`), `NotFoundPage`.
- **`context/HistoryContext.jsx`** is a **cache of the server's per-user history**, not a store: it loads `GET /api/files` on mount and again whenever the signed-in user changes (so a logout never leaves the previous user's list on screen), applies each mutation optimistically, and sends the matching request. It also clears the pre-0XC-100 `tubekeepHistory` / `tubekeepExpired` localStorage keys on mount (`LEGACY_HISTORY_KEYS`); nothing reads them.
- **`context/`** follows the same three-file split for every provider (React Fast Refresh / Biome's `useComponentExportOnlyModules` rule): `xContext.js` (`createContext` + constants), `XContext.jsx` (the provider with all logic), `useX.js` (the hook). This holds for `history*`, `player*`, and **`auth*`** (`authContext.js` / `AuthContext.jsx` / `useAuth.js`). Keep this separation when editing. `AuthProvider` loads `GET /api/auth/me` on mount and exposes `{ user, loading, login(email), logout(), refresh() }`; `user` is `{ email, name, max_storage_bytes }` or `null`.
- **Auth is cookie-based** — the session is a JWT httpOnly cookie the frontend never reads. `lib/media.js` exports **`apiFetch`**: a `credentials: 'include'` wrapper every same-origin API call routes through, which broadcasts the `AUTH_UNAUTHORIZED_EVENT` (`tk:unauthorized`) window event on any 401 so `AuthProvider` drops the user and `ProtectedRoute` bounces to `/login` (session expired). SSE streams (`useDownloadProgress`, `useCloudMove`) pass `{ withCredentials: true }` for the same reason. The auth endpoints themselves (`/api/auth/*`) use plain credentialed `fetch` inside `AuthProvider`, **not** `apiFetch` — a 401 from `/me` is the normal "logged out" signal, not a session-expiry event, so it must not re-broadcast the event.
- **`components/`** — `UrlInput`, `FormatSelector`, `ProgressBar`, `VideoPlayer`, `ProtectedRoute`.
- **Share links:** `/play/:downloadId` is a stable shareable URL (the Share button copies `window.location.origin/play/:id`). It is **exempt from the login gate**. `PlayPage`'s cold-lookup effect first tries `GET /api/files` (session-scoped, since 0XC-100 it returns only the **caller's own** rows) and, if the id isn't there — not the owner, logged out, or the row is expired — falls back to the **public** `GET /api/files/meta/:downloadId` (0XC-112). That endpoint resolves any download by its unguessable id for anyone, no session required, but returns only `{ downloadId, title, thumbnail, type, filename, expired }` — no `user_id`, email, source url, or size — and reports `expired: true` (no filename) whenever there's no local media to serve (still downloading, failed, moved to the owner's cloud, or actually expired), so a non-owner can't distinguish which. It's declared in `routes/files.js` **before** the `/:downloadId/:filename` serve route (which would otherwise swallow `meta/<id>` as `downloadId="meta"`) and before the router's `requireAuth` choke, and is rate-limited separately from the (unthrottled) serve route.
- `VITE_API_URL` defaults to `window.location.origin` when unset (works in single-server mode).

### Styling system — non-obvious
There is **no Tailwind in `package.json`, no `tailwind.config.js`, and no PostCSS.** Tailwind is loaded at runtime from `cdn.tailwindcss.com` in `frontend/index.html`, and the entire Material Design 3 design-token theme (colors like `surface-container-high`, spacing like `gutter`/`stack-lg`, type scale like `headline-md`/`label-md`) is defined inline in the `<script id="tailwind-config">` block there. **To add or change a design token, edit `index.html`, not a config file.** Icons are Material Symbols via Google Fonts, used as `<span className="material-symbols-outlined">icon_name</span>`. Font is Space Grotesk.

**Every `.material-symbols-outlined` span must carry `aria-hidden="true"`.** The glyph is rendered from the span's *text* (the ligature), so an unhidden icon contributes its raw ligature name to the accessible name of whatever contains it — a button reading as `arrow_forward`, or a label announced as `refresh Redownload` (0XC-271). Two consequences follow, and they have to move together: silencing the icon is what makes the surrounding text the accessible name, so **a control whose only content is an icon then needs its own `aria-label`** (`title` alone is a weak fallback — not surfaced on touch, and inconsistently exposed). See `PlayerDock` (four icon-only controls) and `DownloadsPage`'s share/download/delete row for the pattern. `frontend/src/pages/DownloadsPage.jsx`'s `DownloadingCard` is the reference: `aria-hidden` on the icon, `aria-label` on the button, `title` kept for the sighted tooltip.

Related: **a label hidden below a breakpoint uses `sr-only sm:not-sr-only`, never `hidden sm:inline`.** `display: none` removes the text from the accessibility tree too, so at narrow widths the accessible name falls through to whatever is left — which, next to an icon, is the ligature. `sr-only` hides it visually while keeping it named, so one accessible name holds at every width without an `aria-label` overriding the visible text (WCAG 2.5.3, Label in Name). `UrlInput`'s submit button is the call site. `App.css` holds a small amount of legacy plain-CSS for the video player.

`index.html`'s `<style>` block (below the Tailwind config script) also carries a couple of hand-written, non-Tailwind rules: a `--focus-ring` CSS var (light/dark) plus one global `button/a/input/select/[tabindex]:focus-visible` rule, so every interactive element gets one consistent visible-focus ring without per-component styling (0XC-111).

**A button whose disabled state carries a user-facing reason (a tooltip/caption explaining *why*) uses `aria-disabled` + a click guard, not native `disabled`.** Native `disabled` drops the element from the tab order, so a screen reader/keyboard user would never reach the reason. The pattern: `aria-disabled={inactive}` (keep it focusable), an `onClick` guard that no-ops when inactive, and `aria-describedby` pointing at the reason's id. See `FormatSelector.jsx` (pre-existing), `MoveToCloud.jsx`'s "expiring soon" idle button, and `UrlInput.jsx`'s empty-URL submit button. A purely transient in-flight disabled state with no explanatory reason (e.g. `MoveToCloud`'s busy-state trigger, `LoginPage.jsx`'s controls) stays native `disabled`.

## Code Conventions

**Frontend** — ES modules, **no semicolons**, single quotes, 2-space indent, ~100 col, functional components + hooks only. PascalCase component files; the file name matches the default export. Biome ignores unused vars/params prefixed with an underscore (`_foo`).

**Backend** — CommonJS (`require`/`module.exports`), **semicolons**, single quotes, 2-space indent, camelCase files.

API responses are always `{ success: true, data: {...} }` or `{ success: false, error: '...' }`.

Log errors with emoji prefixes for grep-ability (e.g. `❌ Fetch error:`, `⚠️`, `🧹`, `🚀`).

## Deployment

CI/CD lives in `.github/workflows/deploy.yml`. On push to `main` (or manual dispatch):
1. Build a multi-stage Docker image (`Dockerfile`: frontend `npm run build` → Node 22 runtime with `ffmpeg` + `yt-dlp` installed via pip) and push to `ghcr.io/<repo>:latest`.
2. SSH to a Proxmox Docker host **through a Cloudflare Access tunnel** (`cloudflared access ssh`, using CF service-token secrets), then `cd /opt/tubekeep && docker compose pull && docker compose up -d`.

`docker-compose.yml` runs that GHCR image, maps `3001:3001`, sets `DOWNLOADS_DIR=/data/downloads`, and bind-mounts `./downloads:/data/downloads`. The legacy `deploy/ecosystem.config.js` (PM2) is **not** the active path — Docker is. There is no Caddyfile in this repo; TLS/routing is handled externally (Cloudflare).

## Prerequisites
- Node.js 18+ (Docker image uses Node 22)
- `yt-dlp` installed system-wide for local dev (`brew install yt-dlp` on macOS); `ffmpeg` is needed for video+audio merges.
