
## Testing & tooling

```bash
cd backend  && npm test    # node --require ./testSetup.js --test  (node:test, *.test.js beside the source)
cd frontend && npm test    # Playwright a11y smoke suite (npm run test:install on a fresh clone)
```

**IMPORTANT: before creating or modifying any `*.test.js`, `*.spec.js`, test helper, or GitHub Actions workflow — or diagnosing a failing/flaky run — load the `tubekeep-testing` skill.** It carries the rules whose violation fails in a way that points nowhere near the cause: the `testSetup.js` stdout guard, the `spawnServer.js` helper (never hand-pick a `PORT`), the two store contract suites and their per-store escape hatches, the hermetic a11y fixtures, and what CI runs.

Lint/format is [Biome](https://biomejs.dev) via one root `biome.json`; `frontend/` and `backend/` each expose `npm run lint` / `npm run format` that shell out to the same root-installed Biome.

**The root `package.json` is a tooling host and declares no runtime `dependencies` — keep it that way (0XC-333).** It exists only for the shared Biome + `nodemon` install; runtime deps belong to `backend/package.json` and `frontend/package.json`, which own their lockfiles and are what `npm ci` installs in CI and Docker. Node resolves by walking *up*, so a root runtime dep silently substitutes itself whenever `backend/node_modules` is incomplete (partial install, `--omit`, slim image layer) — potentially a breaking major with no error at the failure point, where a clean root manifest fails loudly with `MODULE_NOT_FOUND`. If the root ever genuinely needs a runtime package, document the consumer here and pin it to the same major as `backend/`.

### Dev-server & storage layout

**`backend/nodemon.json` is load-bearing — don't delete it.** Nodemon's default watch is the *entire cwd* for `.js`/`.json` changes, and the downloads directory used to sit inside it — so any write into a watched downloads dir makes **finishing a download restart the dev server**, killing the SSE stream, wiping the job registry and dropping in-flight requests. The browser reports that as a *CORS* error ("CORS request did not succeed. Status code: (null)"), which points nowhere near the cause. `nodemon.json` pins the watch to `src`. Dev only — production runs `npm start` with no watcher.

**Downloads directory is configurable (`DOWNLOADS_DIR`), not hardcoded.** `backend/src/utils/storage.js` resolves it once at load time (`process.env.DOWNLOADS_DIR`, else the historical `backend/downloads`) to an absolute path, and every consumer — routes, cleanup sweep, tests — imports that single `downloadsDir` rather than joining a path itself. `server.js` logs it once at startup (`📁 Downloads directory: …`). Runtime media inside the linted/watched/packaged source tree caused trouble beyond the nodemon restart. `docker-compose.yml` and the `Dockerfile` both set `DOWNLOADS_DIR=/data/downloads` explicitly.

**Single-server mode:** if `frontend/dist/` exists, `backend` serves it statically with an SPA fallback (see `server.js`). So `cd frontend && npm run build` then `cd backend && npm start` serves the whole app on port 3001 with no separate frontend process. This is how production runs.

## Architecture

**Tubekeep** — a yt-dlp-backed video/audio downloader. React SPA (Vite, port 5173 in dev) + Express API (port 3001) + the `yt-dlp` CLI. Downloads land in `<DOWNLOADS_DIR>/<downloadId>/` (default `backend/downloads/`) and stay there until their owner removes them — **nothing expires on a timer**; the per-user quota is what bounds disk use.

### Download flow
1. `GET /api/info?url=...` → `services/ytdlp.js` runs `yt-dlp --dump-json`, returns formats grouped into `{ video, audio, combined }`.
2. `POST /api/download` → mints a `downloadId` (UUID) **and starts the job** server-side. Parameters ride the **request body** (`url`, `formatId`, `type`, `title`, `thumbnail`, `filesize`, `sourceKey`). The job runs to completion **independent of any client connection**. Three guards run before any job starts, in order: (1) client-passed `filesize` against the **per-user quota** (`hasQuotaFor` over `store.usageForUser`) → **507**; (2) the same size against the **global disk** fit margin (`hasRoomFor`) → **507**; (3) the concurrency cap, thrown by `startJob` as `DownloadCapError` → **429**. All are `{ success: false, error }` the UI surfaces inline. Between (2) and (3) the download is **recorded in `downloads`** under the requesting user (`status: 'downloading'`) so it survives a reload — a cap rejection therefore deletes that row again before returning 429, and a failed insert aborts the start with a 500. Terminal hooks (`onComplete`/`onError`, injected into `startJob`) flip the row to `complete` (real filename + on-disk size) or `failed`.
3. `GET /api/download/progress/:downloadId` → **pure observer SSE.** Replays current progress from the registry, then streams `progress`/`complete`/`error` plus `ping` heartbeats every 15s (proxy keep-alive). It **does not spawn a process**; disconnecting only unsubscribes. Reconnecting (reload / new tab / cold visit) **attaches** to the in-flight job — no second process, no query params. An unknown id (e.g. after a restart) yields a terminal `"download not found"` error.
4. `DELETE /api/download/:downloadId` → **explicit cancel.** Aborts the job (`AbortController`), removes partials, drops the caller's history row (`store.deleteForUser`, so another user's id reads as 404) — a cancelled download must not linger in the list or against the quota. Succeeds if *either* half found something; 404 only when neither did. Wired to `DownloadingCard`'s **Dismiss** and the download page **Cancel**.
5. `GET /api/files/:downloadId/:filename` → serves the file with HTTP range support and RFC 5987 `Content-Disposition` for unicode filenames. `?action=download` forces an attachment.

**Download manager (`services/downloadManager.js`)** — an in-memory `Map<downloadId, job>`; each job holds `{ status: 'running'|'complete'|'error', progress, result, error, params, hooks, emitter, abortController }`. Observers attach via `subscribe(downloadId, { onProgress, onComplete, onError })`, which atomically replays current/terminal state then streams live events (returns an unsubscribe fn, or `null` for an unknown id); the `emitter` stays internal so the observer route is a thin SSE serializer. On completion the job builds the SSE payload and awaits `hooks.onComplete` (persisting real filename + size to the `downloads` row — the **only** lifecycle record, nothing on disk) **before** emitting `complete`, so a client reloading the instant it sees the event reads a matching row. Hook failures are caught and logged (`runHook`): a DB blip must never turn a finished download into a failed one. **In-memory only** — an in-flight download dies on restart; terminal jobs are retained ~30 min for late reconnects, then pruned by `sweepJobs`. Cap: `MAX_CONCURRENT_DOWNLOADS` (default **3**). `runningDownloadIds()` exposes ids running *in this process* — the cleanup sweep's "being written to right now" signal.

**Storage guards (`GET /api/disk`, `routes/disk.js`)** — two independent limits, both enforced at `POST /api/download`, both surfaced to the format screen by one endpoint returning `{ total, free, used, sizeMultiplier, headroomBytes, quota: { used, max, remaining } }`.

- **Global free disk**: `hasRoomFor(free, filesize)` — `free >= filesize * DISK_SIZE_MULTIPLIER (2×) + DISK_HEADROOM_BYTES (500 MB)`. The `2×` covers the transient video+audio merge.
- **Per-user quota**: `hasQuotaFor(used, max, filesize)` — `used + filesize <= max`, where `max` is `users.max_storage_bytes` (default 5 GB, **`-1` = unlimited**) and `used` is `SUM(filesize)` of that user's live rows (`NOT expired AND NOT moved AND status <> 'failed'` — an in-flight `downloading` row counts, so parallel starts can't race past the cap). **No** multiplier/headroom: the quota counts what a download *keeps*, not its merge footprint.

Both live in `utils/storage.js`; the frontend reads the same knobs + quota numbers back out of `/api/disk` (`hasRoomFor` / `hasQuotaFor` / `downloadBlockReason` in `lib/media.js`) so client check and server backstop can't drift — the client's `hasQuotaFor` consumes `quota.remaining` rather than re-deriving it, so clamp-at-zero and the `-1` sentinel are defined once, on the server. `FormatSelector` shows a **"Your storage"** banner (used / left, or "unlimited") and disables any format either guard rejects, with the reason under it. Unknown-size formats are never blocked. The client-passed `filesize` is untrusted (a UX guard, not a security boundary) — the row's size is corrected on completion. The guards fail differently: the quota check **fails closed** (a DB outage must not hand out free storage), the disk check **fails open**.

### yt-dlp integration (`services/ytdlp.js`) — read before touching downloads
Deliberate workarounds for YouTube's 2026-era extraction breakage. Do not "simplify" them away:
- **`YOUTUBE_EXTRACTOR_ARGS = 'youtube:player_client=android_vr;formats=missing_pot'`** is passed to *every* invocation. The default web/tv clients need a JS challenge solver broken in yt-dlp 2026.02.x (yields a single 360p format and hangs). `android_vr` restores the full 144p→4K ladder; `formats=missing_pot` keeps formats whose URLs lack a PO Token. Namespaced under `youtube:` so other extractors are unaffected.
- **SABR retries.** YouTube's per-session SABR experiment intermittently strips format URLs. `getVideoInfo` retries metadata up to 4× with back-off until video-only formats appear. `downloadVideo`/`downloadAudio` retry up to 3× on `Requested format is not available|SABR|missing a URL`, with fallback format strings (e.g. `${formatId}+bestaudio/bestvideo+bestaudio/best`) so a vanished exact format still resolves to *something*.
- **Binary & PATH.** Prefers `~/.local/bin/yt-dlp` over the system one, and injects Node's dir into `PATH` because yt-dlp's SABR solver shells out to `node`.
- **Black-holed IPv6, auto-detected at boot (`services/ipv6.js`, 0XC-126).** Where a router advertises an IPv6 route but IPv6 traffic is black-holed, yt-dlp takes **~85s per call instead of ~1.5s** (Python's urllib has no Happy Eyeballs, so it waits out the TCP timeout on each AAAA address). Symptom: `/api/info` spins for a minute-plus, downloads crawl, near-zero CPU. `server.js`'s boot runs `ensureIpv4Decision()` (→ `decideForceIpv4()`) alongside `ensureSchema()`, before `app.listen`: one IPv6 TCP connect to Google Public DNS:53 with a ~2s timeout (`probeIpv6Reachability`), classified connects → `'reachable'` (forcing off), immediate OS rejection → `'no-route'` (ordinary IPv4-only machine, also off), neither before the timeout → `'blackholed'` (warns, returns `true`). The decision feeds `ytdlp.js`'s `setForceIpv4`, so later calls prepend `--force-ipv4`. The probe is **skipped** under `NODE_ENV=test` (mirroring `ensureSchema`'s `DATABASE_URL` skip) so the hermetic suite reaches no network, and is injectable (`probe`/`connect`) so `ipv6.test.js` covers all four outcomes without a socket. **`YTDLP_FORCE_IPV4` overrides the probe** — set it (`true`/`false`) only to force a direction by hand. Diagnose with `curl -6 -m 5 https://www.youtube.com` (hangs) vs `curl -4` (fast).
- Video+audio (`type: 'video'`) merges to mp4 via `--merge-output-format mp4`; `type: 'combined'` downloads a pre-merged format as-is; `type: 'audio'` pulls bestaudio.

### Expire vs. delete (two-tier lifecycle)
A download is **"expired"** when its history row survives but the media is gone, keeping the row visible for re-download. The `downloads` row is the **single** lifecycle record (0XC-109) — no on-disk mirror; a download directory holds only media, and `utils/storage.js` only answers "does this directory exist, and what files does it have" (`getDownloadDir`/`listDownloadDirs`). The **`downloads.expired` column is what the UI reads**. Two destructive operations, both via `DELETE /api/files/:downloadId`, each touching row *and* disk:
- default → `store.expireForUser` + `expireDownload()`: removes the directory, flags the row `expired` + stamps `expired_at`.
- `?permanent=true` → `store.deleteForUser` + `deleteDownload()`: removes row and directory.

At the filesystem level both are the same operation (`expireDownload`/`markMoved` delegate to `deleteDownload`) — the expired/deleted distinction is purely a `downloads`-table concept. Both routes are scoped to the caller's own rows (`user_id` in the `WHERE`), so another user's id reads as `404`.

**No age-based expiry — media is deleted only by its owner.** A download is storage, not a transfer: it stays until the user expires it, deletes it, moves it to their cloud, or supersedes it with a re-download. Disk is bounded by the **per-user quota** instead of a clock, so `MAX_FILE_AGE_HOURS`, `cleanupOldDownloads`, the `keptIds()` skip-set and the standalone `npm run cleanup` CLI are all **gone**. Don't reintroduce a timer sweep: a user who hits their quota gets a `507` and frees space themselves. (`downloads.kept`, `setKeptForUser` and the `PATCH /api/files/:id?kept=` route survive as vestigial — no reader left, kept only to avoid a migration; no UI calls them, and nothing writes the column at download time, so every new row is `false`. The retention note lives on the column in `schema.sql`.)

**Hourly reconcile sweep (`services/cleanup.js`)** keeps the table honest against the filesystem and prunes finished job records (`sweepJobs`). It never removes the media of a download that succeeded. **The order of its steps is load-bearing**:
1. Any `downloading` row whose directory already holds finished media — files present, none of them yt-dlp partials (`.part`/`.ytdl`), job not running in this process — is reconciled to `complete` from the real on-disk file (`store.markComplete(id, patch, { onlyIfDownloading: true })`), picking the largest file exactly as `describeDownloadedFile` does. Covers a completion hook whose DB write was lost (0XC-120). It calls `store.downloadingIds()` first to narrow to the (normally empty) set actually still `downloading`. **Runs before step 3** (0XC-151): it is the only step that can tell a lost completion write apart from a download that really died, and step 3 now deletes what it retires. **It fails closed** — if it throws, step 3 is skipped for that pass, since without a trustworthy answer to "did this row finish?" neither failing it nor deleting its media is safe (same reasoning as the quota check).
2. `expireMissing` marks any completed, live row whose media is gone as expired. With no timer sweep left this only catches media removed **outside the app** (a manual `rm`, a lost volume, a half-finished delete); the `RECONCILE_GRACE_MS` (10 min) window spares a download that landed *during* the sweep and so is missing from its snapshot.
3. `failStale` retires rows genuinely stranded `downloading` by a restart (6h window) **and deletes their directories**. It returns the ids it retired (like `supersedeForUser`) precisely so the sweep can do that: a killed job leaves a `.part` file no user action can ever reach, and a `failed` row is excluded from the quota — so with no age sweep left those bytes would leak permanently.

So none of the three can occupy a user's quota forever. Every step is a `downloads`-table operation, so a `runCleanup()` with no store (unit tests) only prunes job records. The sweep scans the directory once (`listDownloadDirs()`) and derives "still on disk" from that snapshot. The frontend holds the two lists (active + expired) in memory only, re-read from the server — **not** localStorage. (That rule is about *history*; some per-browser preferences do live in localStorage — see **Frontend** below.)

**Re-download dedupe — one row per canonical video identity (0XC-10, refined by 0XC-117):** when a download **completes**, the user's older rows for the same video are hard-deleted (row + media), so a re-download *replaces* the stale entry and the old copy stops occupying the quota. Two states are spared: **moved-to-cloud** rows (media lives in the user's cloud, the row still carries the "Open in …" link) and **`downloading`** rows (a concurrent job that deleting would orphan). Expired, failed and live completed rows all go.

The rule is **server-side**, in the job's `onComplete` hook (`supersedeOlderRows` in `routes/download.js` over `store.supersedeForUser`) — *not* in the browser, where it only ran if a tab happened to witness the SSE `complete` event and so silently never ran (downloads finish server-side regardless of the client, 0XC-25/0XC-26). Running it in the hook is also what makes "only supersede once the new download lands" true: an abandoned or failed re-download leaves the old row intact. `supersededBy` in `HistoryContext.jsx` mirrors the predicate purely so the list updates instantly — it issues **no** requests, and its spared cases must stay in step with `SUPERSEDABLE_SQL` / `isSupersedable` in `downloadsStore.js`.

The match key is the namespaced extractor id — `source_key`, e.g. `youtube:dQw4w9WgXcQ` (`extractor:info.id`, built in `getVideoInfo`, surfaced as `sourceKey` in `/api/info`) — stable across every URL form the same video can be pasted as, and namespaced so two extractors can't collide on a bare id. (Exact `url` equality was 0XC-117's bug: the Redownload button round-trips the URL verbatim so it always matched, but a hand-pasted `youtu.be/…`, `&t=`, `&si=…` variant didn't.) The client carries it from `/api/info` through `POST /api/download`'s body untouched — untrusted input like `filesize`, validated for shape/length by `routes/download.js`'s `isValidSourceKey`, never a security boundary since `supersedeForUser` stays scoped by `userId`. `supersedeForUser` (and its JS mirror `sharesSource`, both in `downloadsStore.js`) matches on `source_key` **only when both sides have one**; whenever either lacks a key — a pre-column row, or an extractor that returned no id — it falls back to exact-`url` match, so nothing regresses. The completion payload threads `sourceKey` through `downloadManager.js`'s `job.result`, so the frontend mirror agrees with the server the moment `complete` lands.

**Pending/failed rows:** downloads finish even if the user leaves the download page, so history rows are written **at click time**, not on SSE completion. `handleDownload` (`InfoPage.jsx`) calls `startPending()` to put a `status: 'downloading'` row into the in-memory list immediately — the server already inserted the real row, this just avoids waiting for a re-sync (fields: `downloadId`, `url`, `type`, `title`, `thumbnail`, `createdAt` — no `filename`/`size` yet). On SSE `complete`, `addDownload(data.data)` replaces it in place with the full record (which carries **no** `status`), rendering as a normal `ActiveCard`; on SSE `error`, `markFailed()` flips it to `status: 'failed'`. `DownloadsPage` routes `status === 'downloading'` → `DownloadingCard` (spinner, links to `/download/:id`, plus **Dismiss**) and `status === 'failed'` → `FailedCard` (Redownload + Dismiss) **before** the `ActiveCard` fallback. These rows exist **server-side too**, so a reload re-reads them — no client-side preservation needed. The two Dismisses differ: a **downloading** row uses `cancelDownload()`, which must `DELETE /api/download/:id` to actually stop the server-side job (abort + remove partials) and also deletes the history row; a **failed** row uses `dismissFailed()`, a hard-delete (`DELETE /api/files/:id?permanent=true`) rather than a move to the expired list, since its file may never have landed.

### Cloud upload ("Move to cloud")

Once a download completes, a visitor can **move** it into their own Dropbox, Google Drive, or OneDrive: upload to the visitor's cloud, then drop the local copy. "Moved" is a **third terminal state** alongside expired/deleted — the row keeps its history card (source `url` + a link into the cloud) but its media is gone, removed by `utils/storage.js`'s `markMoved`. It stops counting toward the quota (`USAGE_WHERE_SQL`/`countsTowardUsage` exclude `moved` rows as they do expired ones). Backend: `services/cloud/` + `routes/cloud.js` (`/api/cloud`). Frontend: `lib/cloud.js`, `hooks/useCloudMove.js`, `components/MoveToCloud.jsx`, `pages/OAuthCallbackPage.jsx`. No provider persists anything — an access token lives only for one upload job, in the tab's `sessionStorage`.

**Load the `tubekeep-cloud-provider` skill before touching any of those files or adding a provider.** It holds the five-function `CloudProvider` contract, `shared.js`, the job manager's concurrency/TTL behaviour, the owner check on `POST /upload`, the PKCE flow, and the three-edit recipe for a new provider.

### Backend (`backend/src/`)
- **`server.js`** — Express entry (helmet with CSP disabled for media + cross-origin resource policy, CORS, morgan), route mounting, static SPA serving, cleanup bootstrap. Sets `app.set('trust proxy', 1)` — production sits behind exactly one hop (Cloudflare straight into the container; no nginx/Caddy) — so `req.ip` is the real visitor, not Cloudflare's edge (0XC-128). **Don't bump this to `true`**: that trusts every hop in a client-supplied `X-Forwarded-For`, letting a client mint unlimited rate-limit buckets by forging entries.
- **`utils/rateLimit.js`** — in-memory sliding-window limiter mounted per-route in `server.js`. Keys each bucket on `CF-Connecting-IP` when present (Cloudflare overwrites it at its edge), else `req.ip`, so local dev and non-Cloudflare deploys still bucket correctly. **Neither header is authenticated by this code**; both are trustworthy only insofar as the deployment guarantees every request transits Cloudflare. `docker-compose.yml` publishes the port directly and nothing here enforces that at the network level, so a request reaching the origin another way can forge either header. Closing it is an infrastructure change (loopback bind behind a Cloudflare Tunnel, or firewall to Cloudflare's IP ranges) — see the 0XC-128 follow-up.
- **`routes/`** — thin HTTP layer: `info.js`, `download.js` (start job / observer SSE / cancel), `files.js` (range serving + public per-item metadata + per-user list + expire/delete), `disk.js`, `cloud.js`. Every router except `info.js` is a **factory** taking the injected store — `createDownloadRouter`/`createDiskRouter`/`createCloudRouter` take `{ store }`, `createFilesRouter(requireAuth, { store })`, `auth.js` the same over `authStore` — so they unit-test against `createMemoryStore()` without Postgres.
- **`services/ytdlp.js`** — all subprocess spawning (see above).
- **`services/ipv6.js`** — boot-time black-holed-IPv6 probe + decision (see above); `server.js` calls it once and feeds the result into `setForceIpv4`.
- **`services/downloadManager.js`** — in-memory job registry decoupled from the client SSE; enforces `MAX_CONCURRENT_DOWNLOADS`. Takes no database dependency — the caller injects `{ onComplete, onError }` hooks into `startJob`.
- **`services/cleanup.js`** — hourly reconcile scheduler (no age-based expiry). Prunes finished job records (`sweepJobs`) and reconciles the table (`markComplete` with `onlyIfDownloading` / `expireMissing` / `failStale`, in that order), deleting the partials of what `failStale` retires.
- **`utils/storage.js`** — source of truth for the directory layout: `getDownloadDir`/`listDownloadDirs` (filesystem-only — which files exist, no lifecycle data), `expireDownload`/`markMoved`/`deleteDownload` (all remove a whole directory), and both storage guards (`getDiskUsage`/`hasRoomFor` + fit constants; `hasQuotaFor`/`remainingQuota` + `UNLIMITED_QUOTA`).
- **`services/downloadsStore.js`** — data access for the `downloads` table (per-user history + quota usage), same shape as `authStore`: `createStore(query)` for production, `createMemoryStore()` for tests. `toApiRow` is the single place DB columns become the API/UI contract; `USAGE_WHERE_SQL` / `countsTowardUsage` are the one quota rule written once per impl — **keep them adjacent, they must change together** (adjacency helps a reader but doesn't stop drift; the contract suite does). The **background workers** outside any request (cleanup sweep, cloud-move job) take the store as an argument from the caller that already holds it (`startCleanupScheduler({ store })`, `createJob({ …, store })`) rather than reaching for a module singleton; omitted in unit tests, where those paths no-op.
- **`utils/friendlyError.js`** — `friendlyYtDlpError(rawMessage)`: maps raw yt-dlp stderr to short, blame-free copy via an ordered `{ pattern, message }` list (unavailable/removed, private, members-only, age-restricted, geo-blocked, live/premiere, unsupported URL, network/timeout), falling back to a generic message. Matches lowercased substrings anywhere in multi-line stderr, most-specific first. `getVideoInfo`'s catch and `downloadManager`'s `runJob` error path both route user-facing errors through it, so `/api/info` and SSE `error` never leak exit codes, extractor tags or enforcement-vendor names. The **full raw stderr is still `console.error`-logged** for operators.

### Auth + database (magic-link login)
Only emails present in a **manually-managed** Neon `users` table can log in — **no signup, no admin UI**; add/remove a user or change their quota by editing the row in the Neon dashboard. Login is an emailed single-use magic link → a JWT httpOnly cookie session.

- **`db.js`** — lazily-created `pg` pool over `DATABASE_URL` (forces TLS). Exposes `query(text, params)` and `getPool()`. Importing it never connects, so tests injecting their own store need no database.
- **`schema.sql`** + **`npm run db:init`** (`src/dbInit.js`) — hand-written schema, no ORM/migrations. Defines `users` (id, email UNIQUE, name, `max_storage_bytes` bigint default 5 GB / `-1` = unlimited), `login_tokens` (stores only the SHA-256 **hash** of each token, single-use + ~15-min expiry), `downloads` (per-user history: lifecycle `status`/`expired`/`moved`+`moved_info`/`kept`, the `filesize` the quota sums, the nullable `source_key` — 0XC-117). Idempotent. `dbInit.js` exports the applier as `applySchema(pool)`; `npm run db:init` is a thin CLI over it, still usable to provision a fresh Neon database. **`server.js` also awaits `applySchema()` on every boot** when `DATABASE_URL` is set (skipped otherwise, e.g. unit tests), then asserts every column `schema.sql` defines is present, so a database missing a column a later commit added self-heals (0XC-115). That required set is **parsed out of `schema.sql` itself** by `src/schemaColumns.js` (`CREATE TABLE` bodies + `ALTER TABLE ADD COLUMN`), not a hand-maintained list, so it covers every table (0XC-129). A failed apply or column assertion is fatal in production (`process.exit(1)`, mirroring the `JWT_SECRET` boot check) and a loud warning in development.
- **`services/mailer.js`** — `sendMagicLink(email, rawToken)`. Sends via the **Resend** HTTP API when `RESEND_API_KEY` is set; otherwise (dev/tests) **logs the link to the server console** so the flow is testable without credentials. Builds links from `APP_URL`, sends from `EMAIL_FROM`. Never throws to the caller (a mail outage must not leak whether an address was allowed) — but it does **log** Resend's `{ data, error }` rejection (status + message), since the SDK resolves rather than throws on an API refusal and an unchecked `await` would swallow every delivery failure.
- **`EMAIL_FROM`'s domain must be Verified in Resend — the repo's most expensive footgun.** An unverified domain means Resend rejects **every** send, so login breaks for *all* users at once rather than degrading, and both things that hide it (the owner-only `onboarding@resend.dev` fallback; Cloudflare-proxied DNS records) have hit this deploy. **Before debugging a login/mail problem anywhere else, read `EMAIL_FROM`'s comment in `backend/.env.example`** — it carries the full trap list and the `dig` commands. Production's value comes from `/opt/tubekeep/.env` on the Docker host via `env_file`, so changing it needs a `docker compose up -d`.
- **`services/authService.js`** — Express/Postgres-free crypto + orchestration (unit-tests in isolation): token `generate`/`hash`, JWT `signSession`/`verifySession` (reads `JWT_SECRET`, 30-day expiry), `requestMagicLink`/`verifyMagicLink`. Token consumption is a single atomic `UPDATE … WHERE used_at IS NULL AND expires_at > now()` in the store — that is what enforces single-use under concurrent clicks.
- **`services/authStore.js`** — data access behind a small interface. `createStore(query)` is the Postgres impl; `createMemoryStore()` implements the same four methods in memory. Routes/middleware take a store so nothing touches Postgres in unit tests. Both impls are held to one contract suite (above).
- **`routes/auth.js`** — `createAuthRouter({ store, mailer })`. `POST /api/auth/request` (rate-limited; **generic response regardless of allowlist**), `GET /api/auth/verify?token=…` (consume → set cookie → redirect to `APP_URL/?login=success|error`), `POST /api/auth/logout`, `GET /api/auth/me` (session user or 401). Cookie flags: httpOnly + SameSite=Lax always, Secure only in prod.
- **`middleware/requireAuth.js`** — `createRequireAuth(store)` verifies the session JWT, loads the user, attaches `req.user` (incl. `user_id`, 0XC-100); 401 otherwise. Mounted on **every** API router (`/api/info`, `/api/download`, `/api/disk`, `/api/cloud`, and `/api/files`'s list/PATCH/DELETE) **except** the public `GET /api/files/:downloadId/:filename` serve route, so shared `/play/:id` links keep working logged-out. CORS runs `credentials: true` against the **pinned** `FRONTEND_URL` (never a wildcard).
- **Deploy ordering** — since every API route requires a session, this backend must ship **together with or after** the frontend login UI (0XC-98); ahead of it, the existing SPA (sending no cookie) 401s and users are locked out. `db.js` verifies the DB's TLS cert by default (`DATABASE_SSL_NO_VERIFY=true` opts out); the server refuses to boot in production without `JWT_SECRET`.

### Frontend (`frontend/src/`)
Routing-based, **not** a single mega-component (the old `App.jsx`-holds-all-state model is gone):
- **`main.jsx`** — `createBrowserRouter`; `<AuthProvider>` wraps `<HistoryProvider>` wraps `<PlayerProvider>` wraps the router. `/login` and `/oauth/callback` are standalone (outside the `App` shell); everything under `/` is in the shell, with the public `play/:downloadId` declared **before** the `<ProtectedRoute>` layout route.
- **`App.jsx`** — layout shell only (header/nav + `<Outlet/>`). Header shows the user's `name` (falling back to email) + **Logout** (`logout()` → `/login`), or a **Log in** link when signed out (so anonymous `/play/:id` visitors can reach login).
- **`components/ProtectedRoute.jsx`** — the login gate: `<Outlet/>` for authed users, redirect otherwise. It also absorbs the magic-link landing — the backend's `GET /api/auth/verify` 302s to `/?login=success|error`, so it strips `?login=success` once the session loads, and on `?login=error` (or any anonymous visit) redirects to `/login` carrying `state.linkError` so the login page explains the expired/invalid link.
- **`pages/`** — `LoginPage` (`/login`, email → `POST /api/auth/request` → generic "check your inbox"; no signup/password), `HomePage` (URL → `/info?url=`), `InfoPage` (format selection), `DownloadPage` (`/download/:id`, runs the SSE), `DownloadsPage` (active + expired), `PlayPage` (`/play/:id`), `NotFoundPage`.
- **`context/HistoryContext.jsx`** is a **cache of the server's per-user history**, not a store: loads `GET /api/files` on mount and again whenever the signed-in user changes (so a logout never leaves the previous user's list on screen), applies each mutation optimistically, sends the matching request. It also clears the pre-0XC-100 `tubekeepHistory` / `tubekeepExpired` localStorage keys on mount (`LEGACY_HISTORY_KEYS`); nothing reads them.
- **`context/` uses a three-file split per provider** (React Fast Refresh / Biome's `useComponentExportOnlyModules`): `xContext.js` (`createContext` + constants), `XContext.jsx` (provider logic), `useX.js` (the hook) — for `history*`, `player*` and `auth*`. **Keep this separation when editing.** `AuthProvider` loads `GET /api/auth/me` on mount and exposes `{ user, loading, login(email), logout(), refresh() }`; `user` is `{ email, name, max_storage_bytes }` or `null`.
- **Every web-storage access goes through `lib/storage.js` (0XC-464)** — `readJson` / `writeJson` / `writeText` / `removeKey`, each taking the store (`localStorage` or `sessionStorage`) as an argument. It is the **only** module in `frontend/src/` that touches `getItem`/`setItem`/`removeItem`, and therefore the only one that catches a web-storage exception. That centralization is the point rather than the de-duplication: both APIs throw in some private modes and on a full origin quota, and a swallowed failure has no symptom by construction — `lib/resume.js` has no UI at all, so a full quota killed resume permanently with nothing to notice. One audited catch is what makes a future dev-mode `console.warn` a single edit. Consumers: `resume.js`, `media.js` (start params), `cloud.js` (tokens), `theme.js`, and `context/HistoryContext.jsx`'s legacy sweep. **Shape validation stays at the call site** — the helpers only guard and parse, so `resume.js` keeps its own `typeof parsed === 'object'` check, which is what makes corrupt stored JSON inert rather than throwing. **`theme.js` uses `writeText`, not `writeJson`, and must keep doing so**: the no-FOUC inline script in `index.html` compares the raw value with `t === 'dark'`, so a JSON-quoted `"dark"` would read as "no preference" and silently reset every existing user to their system default.
- **Resume playback positions (`lib/resume.js`, 0XC-462)** — the player silently picks a video back up where you stopped. It is the deliberate `localStorage` exception to the history rule above, so **don't sweep the `tubekeepResume:*` keys** the way `HistoryContext` sweeps the legacy `tubekeepHistory` / `tubekeepExpired` ones: there is no server column for a playback position and it's per-browser by design. Keys are namespaced **per identity** (`tubekeepResume:<email>`, or `:anon` for logged-out `/play/:id` visitors) so no one resumes another account's copy at their position, and the only reaper is a bounded LRU — never a hook on delete/expire/move, since outliving the media is the point. Every rule lives DOM-free in `lib/resume.js` and the bookkeeping in `hooks/useResumePosition.js` (read their comments before changing a threshold); `PlayerContext.jsx` is the only consumer, and **no component knows the feature exists** — there is no chip, toast or modal by design, the native control bar is the undo. The one non-obvious hazard the hook exists to close: **`logout()` does not stop the dock** and the serve route is public, so a video keeps playing after the session changes — the identity a track writes under is therefore bound on its first write and frozen, or one person's progress would be re-filed under `anon` (where the next visitor on that browser resumes from it) or under whoever logs in next.
- **Auth is cookie-based** — the session JWT is httpOnly and the frontend never reads it. `lib/media.js` exports **`apiFetch`**: a `credentials: 'include'` wrapper every same-origin API call routes through, broadcasting the `AUTH_UNAUTHORIZED_EVENT` (`tk:unauthorized`) window event on any 401 so `AuthProvider` drops the user and `ProtectedRoute` bounces to `/login`. SSE streams (`useDownloadProgress`, `useCloudMove`) pass `{ withCredentials: true }`. The auth endpoints themselves (`/api/auth/*`) use plain credentialed `fetch` inside `AuthProvider`, **not** `apiFetch` — a 401 from `/me` is the normal "logged out" signal, not a session expiry, so it must not re-broadcast the event.
- **`components/`** — `UrlInput`, `FormatSelector`, `ProgressBar`, `VideoPlayer`, `ProtectedRoute`.
- **Share links:** `/play/:downloadId` is a stable shareable URL (Share copies `window.location.origin/play/:id`) and is **exempt from the login gate**. `PlayPage`'s cold-lookup effect first tries `GET /api/files` (session-scoped — since 0XC-100 it returns only the caller's own rows) and, if the id isn't there (not the owner, logged out, or expired), falls back to the **public** `GET /api/files/meta/:downloadId` (0XC-112). That endpoint resolves any download by its unguessable id without a session but returns only `{ downloadId, title, thumbnail, type, filename, expired }` — no `user_id`, email, source url or size — and reports `expired: true` (no filename) whenever there's no local media to serve (still downloading, failed, moved, or actually expired), so a non-owner can't distinguish which. It's declared in `routes/files.js` **before** the `/:downloadId/:filename` serve route (which would otherwise swallow `meta/<id>` as `downloadId="meta"`) and before the router's `requireAuth` choke, and is rate-limited separately from the unthrottled serve route.
- `VITE_API_URL` defaults to `window.location.origin` when unset (works in single-server mode).

### Styling system — non-obvious
There is **no Tailwind in `package.json`, no `tailwind.config.js`, and no PostCSS.** Tailwind loads at runtime from `cdn.tailwindcss.com` in `frontend/index.html`, and the entire Material Design 3 token theme (colors like `surface-container-high`, spacing like `gutter`/`stack-lg`, type scale like `headline-md`/`label-md`) is defined inline in the `<script id="tailwind-config">` block there. **To add or change a design token, edit `index.html`, not a config file.** Icons are Material Symbols via Google Fonts, used as `<span className="material-symbols-outlined">icon_name</span>`. Font is Space Grotesk.

**Every `.material-symbols-outlined` span must carry `aria-hidden="true"`.** The glyph renders from the span's *text* (the ligature), so an unhidden icon contributes its raw ligature name to the accessible name of whatever contains it — a button reading as `arrow_forward`, a label announced as `refresh Redownload` (0XC-271). Two consequences that must move together: silencing the icon is what makes the surrounding text the accessible name, so **a control whose only content is an icon then needs its own `aria-label`** (`title` alone is a weak fallback — not surfaced on touch, inconsistently exposed). See `PlayerDock` (four icon-only controls) and `DownloadsPage`'s share/download/delete row; `DownloadsPage.jsx`'s `DownloadingCard` is the reference (`aria-hidden` on the icon, `aria-label` on the button, `title` kept for the sighted tooltip).

Related: **a label hidden below a breakpoint uses `sr-only sm:not-sr-only`, never `hidden sm:inline`.** `display: none` removes the text from the accessibility tree, so at narrow widths the accessible name falls through to what's left — next to an icon, the ligature. `sr-only` hides it visually while keeping it named, so one accessible name holds at every width without an `aria-label` overriding visible text (WCAG 2.5.3, Label in Name). `UrlInput`'s submit button is the call site. `App.css` holds a little legacy plain-CSS for the video player.

`index.html`'s `<style>` block (below the Tailwind config) also carries hand-written non-Tailwind rules: a `--focus-ring` CSS var (light/dark) plus one global `button/a/input/select/[tabindex]:focus-visible` rule, so every interactive element gets one consistent visible-focus ring without per-component styling (0XC-111).

**A button whose disabled state carries a user-facing reason (a tooltip/caption explaining *why*) uses `aria-disabled` + a click guard, not native `disabled`.** Native `disabled` drops the element from the tab order, so a keyboard/screen-reader user would never reach the reason. The pattern: `aria-disabled={inactive}` (keep it focusable), an `onClick` guard that no-ops when inactive, `aria-describedby` pointing at the reason's id. See `FormatSelector.jsx`'s over-quota Get button and `UrlInput.jsx`'s empty-URL submit button. A purely transient in-flight disabled state with no explanatory reason (`MoveToCloud`'s busy trigger, `LoginPage.jsx`'s controls) stays native `disabled`.

## Code Conventions

**Frontend** — ES modules, **no semicolons**, single quotes, 2-space indent, ~100 col, functional components + hooks only. PascalCase component files; the file name matches the default export. Biome ignores unused vars/params prefixed with an underscore (`_foo`).

**Backend** — CommonJS (`require`/`module.exports`), **semicolons**, single quotes, 2-space indent, camelCase files.

API responses are always `{ success: true, data: {...} }` or `{ success: false, error: '...' }`.

Log errors with emoji prefixes for grep-ability (e.g. `❌ Fetch error:`, `⚠️`, `🧹`, `🚀`).

## Environment Variables

**`backend/.env.example` and `frontend/.env.example` are the authoritative reference** — every variable, with the reasoning, the traps and the diagnostic commands. Read the relevant one before changing or adding config; keep it updated when you add a variable.

Secrets (`DATABASE_URL`, `JWT_SECRET`, `RESEND_API_KEY`, `DROPBOX_APP_SECRET`, `GOOGLE_CLIENT_SECRET`) live only in `backend/.env` (gitignored) — never commit them.

## Deployment

CI/CD lives in `.github/workflows/deploy.yml`. On push to `main` (or manual dispatch):
1. Build a multi-stage Docker image (`Dockerfile`: frontend `npm run build` → Node 22 runtime with `ffmpeg` + `yt-dlp` installed via pip) and push to `ghcr.io/<repo>:latest`.
2. SSH to a Proxmox Docker host **through a Cloudflare Access tunnel** (`cloudflared access ssh`, using CF service-token secrets), then `cd /opt/tubekeep && docker compose pull && docker compose up -d`.

`docker-compose.yml` runs that GHCR image, maps `3001:3001`, sets `DOWNLOADS_DIR=/data/downloads`, and bind-mounts `./downloads:/data/downloads`. The legacy `deploy/ecosystem.config.js` (PM2) is **not** the active path — Docker is. There is no Caddyfile in this repo; TLS/routing is handled externally (Cloudflare).

## Prerequisites
- Node.js 18+ (Docker image uses Node 22)
- `yt-dlp` installed system-wide for local dev (`brew install yt-dlp` on macOS); `ffmpeg` is needed for video+audio merges.
