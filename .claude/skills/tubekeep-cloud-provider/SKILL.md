# Tubekeep cloud upload ("Move to cloud")


Once a download completes, a visitor can **move** it into their own Dropbox, Google Drive, or OneDrive: upload to the visitor's cloud, then drop the local copy. "Moved" is a **third terminal state** alongside expired/deleted — the row keeps its history card (source `url` + a link into the cloud) but its media is gone, removed by `utils/storage.js`'s `markMoved` (which since 0XC-109 delegates to `deleteDownload`; "moved" lives purely in the row's `moved`/`moved_info` columns). It stops counting toward the quota — `USAGE_WHERE_SQL`/`countsTowardUsage` exclude `moved` rows as they do expired ones. This supersedes `docs/cloud-upload-design.md`'s "Model A"; that doc is now a historical design record.

**Provider registry & contract (`backend/src/services/cloud/`).** `index.js`'s `getProvider(name)` / `listEnabledProviders()` are the only way routes or the job manager reach a provider — nothing imports `dropbox.js`/`googledrive.js`/`onedrive.js` directly, which is what let OneDrive (0XC-13) slot in without touching routes, job manager or UI. A `CloudProvider` implements five functions: `isEnabled()`, `getPublicConfig()` (the non-secret `{ clientId, redirectUri }` the frontend may read), `exchangeCode({ code, codeVerifier, redirectUri })`, `refresh({ refreshToken })`, `upload({ accessToken, filePath, fileName, size, onProgress, signal })` (streams from disk, returns `{ path, name, link }`). `shared.js` hoists what providers duplicated (0XC-93): the `CloudError` type (`code` + optional `status`), the OAuth `postToken` relay POST, the `refresh` shell, `withRetry` (retries only 5xx/network — auth and quota errors are terminal, and a cancelled upload throws a classified `aborted` `CloudError` instead of looking transient), the shared 8 MB `DEFAULT_CHUNK_SIZE`, and `makeProgressReporter`. Every provider publishes `clientId` from `getPublicConfig`. Dropbox uses the official `dropbox` SDK for chunked upload sessions above the 8 MB single-shot threshold and builds a no-scope path-based deep link into `/Apps/<DROPBOX_APP_FOLDER>/`. Google Drive hand-rolls the same shape against Drive's resumable-upload REST API (raw `fetch`, no SDK), scoped to `drive.file` (app-created files only, so no sensitive-scope review) and finds-or-creates a `GOOGLE_DRIVE_FOLDER` in My Drive. OneDrive does the same against Microsoft Graph and is the one **public client** — no app secret at all (`MS_CLIENT_ID` + `MS_REDIRECT_URI`), PKCE alone, with `Files.ReadWrite.AppFolder` confining uploads to `/me/drive/special/approot`; the `common` authority accepts both personal and work/school accounts. No provider persists anything — an access token lives only for one upload job.

**Routes & job manager.** `routes/cloud.js`'s `createCloudRouter({ store })` mounts at `/api/cloud`: `GET /providers` (public config for enabled providers only — how the frontend hides "Move to cloud" when none are configured), `POST /oauth/token` / `POST /oauth/refresh` (stateless PKCE relay — the app secret never leaves the server; tokens go to the browser, nothing is persisted), `POST /upload` (checks `store.findForUser` so **only the download's owner can move it** — the id alone would otherwise let one signed-in user copy another's file into their cloud — then hands off to `services/cloud/jobs.js`'s `createJob`, returning only an opaque `jobId`), `GET /upload/:jobId/progress` (SSE — the URL carries just the `jobId`, which is why the access token rides the `POST /upload` body rather than a query string). `jobs.js` is an in-memory registry shaped like the download manager: `MAX_CONCURRENT` (3) with the rest queued, a hard TTL (30m) that aborts and fails an abandoned job, and a 2m linger after settling so a reconnecting SSE client can read the outcome. On success it calls `markMoved()` and best-effort mirrors the flag onto the caller's row via the injected `store` — a DB blip must not fail an upload that already succeeded (mirroring `runHook`). Disconnecting the SSE stream does **not** abort the upload; only the hard TTL or a genuine provider failure can.

**Frontend.** `lib/cloud.js` is provider-agnostic, data-driven by one `PROVIDERS` table: it runs the PKCE flow (Web Crypto `S256`), opens the consent popup, and keeps tokens in `sessionStorage` only (dies with the tab) — `getFreshAccessToken(name)` transparently refreshes via the backend relay near expiry and otherwise throws a `NOT_CONNECTED`-coded error so callers know to prompt a (re)connect. `pages/OAuthCallbackPage.jsx` is the `/oauth/callback` route the popup lands on — standalone, outside the `App` shell, relaying `{ code, state }` to the opener via `postMessage` (targeted at the exact origin) and closing itself. `hooks/useCloudMove.js` drives one move end to end (lazy connect → `POST /api/cloud/upload` → SSE by `jobId` → flags the row moved in `HistoryContext`) through a `phase` machine (`idle | connecting | starting | queued | uploading | complete | error`). `components/MoveToCloud.jsx` is the UI on that hook: hidden until the enabled-providers list resolves (avoids a flash-then-disappear) and when none are configured, disabled with an "Expiring soon" nudge once remaining runway drops under 15 minutes (so a move can't outlive its source file), and on failure offers "download instead" alongside "Try again". Since 0XC-11 it renders in **both** `DownloadsPage` and `VideoPlayer` (`/play/:id`).

Each provider is independent; one missing any required var is cleanly omitted from `listEnabledProviders()` rather than erroring. To add a **new** provider: implement the five functions in `services/cloud/<name>.js` (reusing `shared.js`), register it in `services/cloud/index.js`'s `PROVIDERS` map, and add its metadata (`label`, `icon`, `authEndpoint`, `scopes`, optional `authParams`/`configKey`, `viteClientId`, `viteRedirect`) to `lib/cloud.js`'s `PROVIDERS` table — nothing in `routes/cloud.js`, `jobs.js`, `useCloudMove.js` or `MoveToCloud.jsx` changes. OneDrive (0XC-13) is the worked example: those three edits plus `docs/onedrive-setup.md`.
